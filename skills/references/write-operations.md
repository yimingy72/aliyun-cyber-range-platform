# 写操作流程

对工具契约中标为**写操作**的每个工具使用本流程。

## 调用前

1. 确认用户明确要求该项变更，并用只读工具定位准确目标 ID。
2. 展示目标、影响范围和不可逆后果；销毁、镜像删除、用户角色/状态、密码和云配置变更必须特别明确。
3. 检查实例或批次状态。不要对不兼容状态发起销毁、重试、重启或打包。
4. 创建前确认模板/镜像对调用者可见。单实例读取 [instance-specifications.md](./instance-specifications.md)，不要猜测 CPU、内存、数量或过期时间。

## 独立靶机创建的必经顺序

1. 确认平台镜像、CPU、内存、数量、过期时间及准确影响范围。
2. 用相同 CPU/内存调用 `single_instance_spec_check`。返回不是 `exactAvailable: true`，或调用报错/超时时停止；不得尝试创建。
3. 校验成功后立即以稳定 `idempotencyKey` 首次调用 `single_instance_batch_launch`。CPU/内存有任何变化时回到第 2 步；服务端会再次校验。
4. 若首次响应返回 `confirmationId`，向用户展示影响摘要并等待明确确认；再以完全相同的业务参数、同一幂等键和该 ID 第二次调用。没有服务端确认要求时，不编造 `confirmationId`。

## 用户授权与平台确认

用户明确授权是所有写操作的前提。当前工具接受的 `idempotencyKey`、`confirmationId` 是可选操作元数据，不能代替用户授权。

- 若服务端直接接受操作：只在已取得用户明确授权后执行。
- 若服务端返回 `CONFIRMATION_REQUIRED` 和 `confirmationId`：核对摘要与用户请求一致，再以完全相同的业务参数和该 `confirmationId` 二次调用。
- 若当前 schema 或响应要求 `idempotencyKey`：为同一请求使用稳定键；参数或目标改变时使用新键并重新取得用户授权。
- 不要编造 `confirmationId`，也不要预设所有部署都会返回它。

返回操作、实例、批次或作业 ID 只表示“已受理”，不表示云操作已完成。

## 跟踪与清理

- 创建、重试、销毁、重启或打包后，查询结果实例或作业，直到其进入终态。
- 如果用户授权 smoke test，在观察到成功条件后立即销毁创建的资源，再确认 `destroyed` 或相应终态。
- 若因权限、可见性、状态或容量失败，报告准确阻塞原因；不要暴力重试。
- 不要通过未暴露接口绕过清理流程。

## 修改配置和身份

- 调用 `cloud_config_update` 前，先调用 `cloud_config_get`；只修改用户明确要求的字段。不要将脱敏密钥视为可用值。
- 未经用户明确授权和 `userId` 解析，不要重置密码、修改角色或禁用用户。
- 发布、停用或删除镜像前，确认 owner/admin 权限，并说明会改变可见性、可用性还是删除资产。
