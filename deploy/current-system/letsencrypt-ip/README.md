# Public IP HTTPS with Let’s Encrypt

This optional deployment keeps the existing public IP, routes, and Keycloak management allowlist. It uses Certbot 5.4 or newer with the `shortlived` ACME profile and HTTP-01 on public TCP port 80. The `caddy-direct` service reads the certificate and challenge directory through read-only mounts. Certbot and the renewal timer run only on the proxy host.

1. Use `/opt/cyber-range-public-ip-tls` as `RANGE_IP_TLS_DIR`. Create `caddy-config`, `caddy-data`, `letsencrypt`, `webroot`, and `logs` there. Restrict the parent directory to root. Copy the active Caddyfile to `caddy-config/Caddyfile` and save a separate backup of it and the existing Caddy `/data`. Seed `caddy-data` with the existing `/data` so the internal CA remains available for rollback. Append `http.caddy` to the copied Caddyfile. Keep the HTTPS routes and access restrictions as they were.
2. Append this directory’s `compose.yml` to the host’s normal Compose invocation. Validate the candidate, then recreate only `caddy-direct` with `--no-deps`. Confirm the current HTTPS certificate still works and only `/.well-known/acme-challenge/*` bypasses the HTTP redirect. Retain this overlay in later releases when recreating Caddy.
3. Copy `manage-ip-certificate.sh` into `RANGE_IP_TLS_DIR`, with execute permission. Create a root-owned `settings.env` beside it with `PUBLIC_IP`, `CADDY_CONTAINER`, and `CERTBOT_IMAGE` set to the installed Certbot image’s immutable ID or digest. Save a compressed Docker image archive there as `certbot-image.tar.gz` so scheduled renewals can restore it after image cleanup. Run the script with `issue-dry-run`, then `issue`. Check the production certificate’s IP SAN and trust chain.
4. Replace the active HTTPS block’s `tls internal` with `tls /etc/letsencrypt/live/<PUBLIC_IP>/fullchain.pem /etc/letsencrypt/live/<PUBLIC_IP>/privkey.pem`. Validate and reload Caddy. Verify the public certificate and HTTPS routes from a client with only public roots.
5. Install the `.service` and `.timer` files under `/etc/systemd/system`, reload systemd, and enable `cyber-range-ip-certificate.timer`. The service checks every six hours and retries failures after 15 minutes, with at most three starts per hour. It reloads Caddy only if the live certificate differs from the valid one on disk, and verifies the served fingerprint after reloading. If an earlier reload failed, the next run retries even when Certbot has nothing to renew.

To check renewal without changing the certificate, run `manage-ip-certificate.sh renew-dry-run`. To prove the complete production renewal path, run `manage-ip-certificate.sh renew-force` once and confirm the public serial changed. Do not schedule forced renewals. Check the next scheduled run with `systemctl list-timers cyber-range-ip-certificate.timer` and check failures with `journalctl -u cyber-range-ip-certificate.service`.

To roll back, stop and disable the timer, let any active renewal finish, restore the saved Caddyfile to `caddy-config/Caddyfile`, and validate and reload Caddy. Keep the mounted `caddy-data`: it contains the previous CA. Clients will again need to trust that CA until the public certificate is restored.
