# 阿里云综合靶场竞赛平台实施计划

- 日期：2026-06-23
- 关联设计文档：[2026-06-23-cloud-cyber-range-saas-design.md](/Users/yym/Documents/阿里云For综合靶场竞赛平台/docs/superpowers/specs/2026-06-23-cloud-cyber-range-saas-design.md)
- 目标阶段：第一阶段 PoC

## 1. 计划目标

本计划的目标不是一次性做完整 SaaS，而是尽快交付一个可运行的最小闭环：

`管理员创建比赛/队伍 -> 选择靶场模板 -> 平台为队伍创建独立 VPC + ECS 靶场 -> 平台展示状态与入口 -> 平台销毁靶场`

实施策略：

- 先打通最短链路，再补后台页面
- 先保证创建/销毁/状态可靠，再谈扩展
- 先做单体单仓，再为后续拆分预留边界

## 2. 总体里程碑

### Milestone 0：工程初始化

目标：把仓库变成可开发、可运行、可迭代的基础项目。

交付物：

- 前后端单仓项目骨架
- PostgreSQL 本地开发环境
- Docker Compose 开发环境
- 基础环境变量管理
- 基础日志能力

验收标准：

- 本地一条命令能启动数据库和应用
- 管理后台首页可访问
- API 健康检查可访问

### Milestone 1：核心领域模型与后台骨架

目标：建立最小可支撑编排的平台数据骨架。

交付物：

- `Competition`
- `Team`
- `RangeTemplate`
- `RangeInstance`
- `ProvisionJob`
- `ProvisionJobStepLog`

验收标准：

- 管理员可登录后台
- 可创建比赛
- 可创建队伍
- 可录入靶场模板元数据
- 数据库迁移可重复执行

### Milestone 2：最小 IaC 执行能力

目标：在不接复杂业务流程的前提下，先跑通最小阿里云环境创建与销毁。

交付物：

- 一份最小 OpenTofu 模块
- Runner 执行器原型
- 本地/服务端执行工作目录规范
- 输出结果采集能力

验收标准：

- 可通过命令或内部接口触发：
  - 创建 1 个 VPC
  - 创建 1 台 ECS
  - 读取 outputs
  - 执行 destroy
- 执行日志和退出码可落库或落文件

### Milestone 3：编排主链路打通

目标：让“后台操作 -> 任务创建 -> Runner 执行 -> 状态回写”真正贯通。

交付物：

- `ProvisionJob` 状态机
- 应用内 Worker
- 创建靶场 API
- 销毁靶场 API
- 实例状态回写

验收标准：

- 后台点击“创建靶场”后可自动生成任务
- 任务执行成功后实例状态为 `running`
- 输出访问入口可展示在后台
- 销毁成功后实例状态为 `destroyed`

### Milestone 4：管理台可视化与异常处理

目标：让平台从“能跑”升级为“能用、能排错”。

交付物：

- 环境实例列表页
- 任务中心页
- 步骤日志查看页
- 异常实例视图
- 重试操作

验收标准：

- 管理员能看见任务过程
- 创建失败能看到错误摘要
- 可对失败任务执行重试
- 可对残留环境执行销毁

### Milestone 5：稳定性与模板收敛

目标：为后续扩展到多机综合靶场和混合云资源做准备。

交付物：

- 多机 ECS 靶场模板 v1
- CIDR 池分配逻辑
- 过期回收任务
- 模板版本化约定
- 镜像生产流程说明

验收标准：

- 可创建一套多台 ECS 的综合靶场
- 可按队伍分配独立网段
- 到期环境可自动进入销毁流程

## 3. 推荐实施顺序

推荐不要按“先前端、后后端、最后云脚本”的顺序开发，而是按下面顺序推进：

1. 仓库基础骨架
2. 数据模型与管理后台最小 CRUD
3. 最小 OpenTofu 模块
4. Runner 执行器
5. ProvisionJob 状态机
6. 创建链路
7. 销毁链路
8. 任务日志与异常处理
9. 多机综合靶场模板

## 4. 建议代码结构

第一版建议使用单仓结构：

```text
apps/
  web/                # Next.js 管理后台 + 轻官网
  api/                # NestJS API + Worker

packages/
  database/           # Prisma schema, migrations, seed
  shared/             # 类型、常量、DTO、状态枚举
  iac-runner/         # OpenTofu 执行封装
  template-sdk/       # 模板元数据校验、变量渲染

infra/
  opentofu/
    modules/
      alicloud-vpc-single-ecs/
      alicloud-range-multi-ecs/
  packer/
    templates/

docs/
  superpowers/
    specs/
    plans/
```

## 5. 每个里程碑的具体任务

### 5.1 Milestone 0 任务拆解

- 初始化 `pnpm workspace`
- 创建 `apps/web`
- 创建 `apps/api`
- 创建 `packages/database`
- 接入 PostgreSQL
- 配置 Prisma
- 配置 Docker Compose
- 建立 `.env.example`
- 增加基础日志与 health check

建议完成后立即验证：

- `web` 可启动
- `api` 可启动
- `db` 可连接

### 5.2 Milestone 1 任务拆解

- 设计 Prisma schema
- 创建数据库迁移
- 实现管理员登录最小方案
- 完成比赛管理 CRUD
- 完成队伍管理 CRUD
- 完成模板管理 CRUD
- 完成环境实例列表基础接口

建议先不做复杂 RBAC。

### 5.3 Milestone 2 任务拆解

- 编写阿里云 Provider 基础配置
- 建立最小 `alicloud-vpc-single-ecs` 模块
- 约定变量输入格式
- 约定 outputs 格式
- 封装 `init/plan/apply/output/destroy`
- 约定工作目录生命周期

这里的重点不是页面，而是：

- Runner 稳定执行
- Runner 可收集结果
- Runner 失败时可诊断

### 5.4 Milestone 3 任务拆解

- 实现 `ProvisionJob` 创建逻辑
- 实现应用内 Worker 轮询
- 增加任务加锁与并发保护
- 增加创建靶场服务
- 增加销毁靶场服务
- 回写实例状态与访问入口
- 增加操作审计记录

这里是第一阶段最核心的里程碑。

### 5.5 Milestone 4 任务拆解

- 环境实例页展示状态与操作按钮
- 任务中心页展示最近任务
- 任务详情页展示步骤日志
- 增加“重试创建/重试销毁”
- 增加“异常实例”筛选

第一版 UI 不追求炫，但必须可判断：

- 任务卡在哪一步
- 环境现在是什么状态
- 管理员下一步该点什么

### 5.6 Milestone 5 任务拆解

- 把最小单机模板扩展为多机模板
- 设计模板版本字段与兼容规则
- 增加 CIDR 池管理
- 实现过期回收 Worker
- 补充镜像版本记录
- 编写第一版运维手册

## 6. 测试与验证安排

### 6.1 开发早期测试

每完成一个里程碑至少做 3 类检查：

- 单元测试
- 本地集成测试
- 手工演练

### 6.2 最关键的真实验证链路

从 Milestone 2 开始，必须反复验证：

`创建 VPC -> 创建 ECS -> 获取输出 -> destroy`

等 Milestone 5 时再升级到：

`创建 VPC -> 创建多台 ECS -> 写回入口 -> destroy`

### 6.3 回归清单

每次改动后至少检查：

- 重复点击不会重复创建任务
- 同一实例不会被并发创建两次
- 创建失败不会误显示成功
- 销毁失败环境能被重新处理
- 审计日志能追踪操作来源

## 7. 风险与应对

### 风险 1：阿里云资源创建慢或不稳定

应对：

- 所有云操作异步化
- 每一步都记录日志与耗时
- 不在 HTTP 请求中同步等待

### 风险 2：IaC 执行目录混乱导致串环境

应对：

- 约定每个 `ProvisionJob` 独立工作目录
- 工作目录与实例 ID、任务 ID 绑定
- destroy 默认回到对应实例目录

### 风险 3：镜像准备过慢拖慢整体节奏

应对：

- 先用最小基础镜像验证流程
- 再逐步引入 Packer 预制镜像
- 不把第一阶段卡死在复杂镜像工厂上

### 风险 4：后台做太多，主链路迟迟不通

应对：

- 所有开发排期都以创建/销毁闭环优先
- 页面和视觉优化排在主链路之后

## 8. 第一周建议行动

如果你准备正式开工，我建议第一周只做下面这些：

1. 初始化 monorepo、Next.js、NestJS、Prisma、PostgreSQL
2. 建立 6 个核心表
3. 完成管理员登录和比赛/队伍/模板最小 CRUD
4. 写第一份最小 OpenTofu 模块
5. 手工从命令行跑通最小阿里云创建/销毁

只要第一周能做到第 5 点，整个项目就已经走在很对的路上了。

## 9. 第二周建议行动

1. 做 `ProvisionJob` 状态机
2. 做应用内 Worker
3. 把后台按钮接到创建任务
4. 回写实例状态和 outputs
5. 打通销毁流程

第二周结束的目标是：

> 管理员在后台点一下，就真的能为队伍拉起一套最小靶场，再从后台销毁。

## 10. 可延期事项

这些内容可以明确后移，不要抢第一阶段资源：

- 多租户
- 复杂权限
- 选手前台
- 品牌官网精修
- 多云抽象真实落地
- 混合云资源模板
- 模板市场
- 复杂告警系统

## 11. 完成判断

当下面这些都成立时，可以认为 implementation plan 已执行到第一阶段目标：

- 管理员能管理比赛、队伍、模板
- 平台能按队伍创建独立 VPC 靶场
- 平台能展示状态、入口、日志
- 平台能销毁资源
- 失败可见、可重试、可定位
- 一套最小多机靶场能在真实阿里云环境稳定重复创建和销毁
