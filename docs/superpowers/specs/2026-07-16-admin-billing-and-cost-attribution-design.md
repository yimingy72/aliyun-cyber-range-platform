# 后台账单费用模块与阿里云真实账单归属设计

日期：2026-07-16
状态：Active

## 当前状态快照

截至当前仓库状态，下面这些基础能力已经存在，可直接复用：

1. 后台已经有统一工作台壳层、左侧导航和 admin 专属页面结构
2. 平台已经有 `admin / user` 两种角色和基于当前登录用户的权限收口
3. 编排实例、单实例、平台镜像和个人镜像已经补齐 `ownerUserId` 主线
4. OpenTofu 与 worker 主链路已经会把已创建云资源写回 `resourceSummary`
5. 现有资源记录中已经能看到 ECS、云盘、EIP、NAT、SNAT、DNAT、镜像等云资源 ID 的主要落点

当前还没有的能力主要是：

1. 后台没有 `账单费用` 模块
2. 平台没有“平台创建资源 -> 本地计费台账 -> 阿里云真实账单回收”的完整闭环
3. 资源创建链路没有统一的账单标签规范
4. 没有面向 admin 的平台总账单、用户账单、资源级账单明细与导出能力
5. 没有“未归属异常账单”的对账告警机制

## 1. 背景

平台现在已经进入多用户共用阶段，但阿里云账号仍是公共账号，且存在多人混用历史。因此账单模块不能直接把整个阿里云账号的账单搬进平台，而必须严格收口为：

1. 只统计平台上线之后产生的费用
2. 只统计平台创建出来的资源费用
3. 所有平台资源必须能映射回平台或具体平台用户
4. 用户账单必须来自阿里云真实账单，而不是平台内部估算

本次设计的核心不是“做一个新页面”，而是补一条完整主链：

- 平台创建资源时强制标记归属
- 本地保存资源归属台账
- 定时同步阿里云真实账单
- 按资源维度回收并映射到平台用户或平台公共费用
- 仅对 admin 提供查看与导出能力

## 2. 本次目标

本次设计覆盖以下目标：

1. 在后台左侧导航 `用户管理` 下新增 `账单费用` 模块
2. `账单费用` 模块只允许 `admin` 可见和可访问，普通用户完全不可见
3. 账单金额统一基于阿里云真实账单，默认展示应付金额
4. 默认查询时间范围为最近 30 天，并支持任意时间范围查询
5. 平台支持查看：
   - 平台总账单概览
   - 用户账单列表
   - 单个用户账单明细
   - 资源级账单明细
6. 支持 CSV / Excel 导出
7. 自 `2026-07-16` 起，所有平台创建的计费资源都必须带统一标签，并写入本地账单资源台账
8. 费用覆盖创建和使用中的持续成本，不只覆盖“创建动作”，至少包含：
   - ECS 实例
   - 系统盘 / 数据盘
   - 公网带宽 / 流量 / EIP
   - NAT Gateway / SNAT / DNAT
   - 自定义镜像 / 快照 / 镜像衍生存储
9. 平台公共资源费用只计入平台总账单，不分摊给用户
10. 对无法归属的异常账单保留后台告警和明细追踪能力

## 3. 非目标

本轮不处理以下内容：

1. 不对没有平台标签或无法命中平台账单资源台账的历史账单做平台内归属
2. 不统计非平台创建的阿里云资源费用
3. 不按 AK / SK 维度做费用归属
4. 不在首期引入平台公共费用按用户分摊逻辑
5. 不向普通用户开放任何账单入口
6. 不在首期接入复杂财务审批、付款、结算单流程
7. 不做跨云厂商统一账单模型

## 4. 核心产品规则

### 4.1 生效边界

账单模块只统计满足以下条件的费用：

1. 对应资源由平台创建
2. 资源存在平台标签或能命中本地账单资源台账
3. 资源账单时间晚于该资源在本地台账中的 `billingStartAt`

不满足以上任一条件的账单，不进入平台账单视图。

`2026-07-16` 是平台账单标签和本地账单资源台账的首个生效日，不再作为唯一过滤条件；真正的认账边界以“是否命中平台标签 / 台账”为准。

### 4.2 权限规则

权限固定如下：

1. `admin` 可以看到左侧导航中的 `账单费用`
2. `admin` 可以访问账单页、账单接口、导出接口和异常账单列表
3. 普通 `user` 完全看不到 `账单费用` 导航
4. 普通 `user` 直接访问账单路由或接口时必须被拒绝

### 4.3 金额口径

页面默认展示阿里云真实账单中的应付金额。

首期不把“现金实付金额”作为默认主口径，不在列表层同时展开原价、优惠、抵扣等多种金额视图，避免首屏复杂度过高。后续如需补充，可在明细层增加更多金额字段。

### 4.4 平台公共费用规则

如果某类资源明确属于平台，但不属于某个具体用户，则：

1. 记为 `platform` 归属
2. 只进入平台总账单
3. 不分摊给用户

### 4.5 归属完整性规则

从 `2026-07-16` 起，平台创建的计费资源必须满足：

1. 云上有统一标签
2. 本地有资源归属台账
3. 云账单回收时能按资源维度映射到：
   - 具体用户
   - 平台公共费用

如果出现“平台资源已产生账单，但无法归属”的情况，不能静默忽略，必须记为异常账单并暴露给 admin。

## 5. 账单归属主线

### 5.1 为什么不能按 AK / SK 归属

阿里云账单按账号和资源归集，而不是按访问凭证归集。即使平台使用独立 AK / SK 调用云 API，也不能假设“该 AK / SK 查到的就是该 AK / SK 产生的账单”。

因此平台账单归属的可靠主线必须是：

1. 平台创建资源时写入归属标签
2. 本地记录资源归属台账
3. 账单同步时按资源 ID 和标签回收

### 5.2 主线设计结论

本次明确采用：

1. **阿里云真实账单作为金额真相**
2. **本地账单资源台账作为归属真相**

页面和导出只展示两者都能成立的账单结果。

## 6. 云资源标签规范

### 6.1 必备标签

平台从 `2026-07-16` 起创建的所有计费资源都必须打统一标签。首期建议至少包含：

1. `CreatedBy=cyber-range-platform`
2. `PlatformScope=user|platform`
3. `PlatformUserId=<平台用户ID，平台公共资源为空>`
4. `RangeInstanceId=<编排实例ID，可空>`
5. `SingleInstanceBatchId=<单实例批次ID，可空>`
6. `PlatformImageAssetId=<平台镜像资产ID，可空>`
7. `BillingStartAt=2026-07-16`

### 6.2 标签原则

标签的目标是“可追溯”，而不是承载全部业务状态。因此：

1. 标签字段数量保持最小必要集
2. 用户归属优先用稳定 ID，不用用户名
3. 允许部分业务字段为空，但 `CreatedBy`、`PlatformScope`、`BillingStartAt` 必须存在
4. 本地资源台账需要保存创建时的标签快照，避免后续云上标签变更后影响对账

### 6.3 适用资源范围

标签至少要覆盖以下资源类型：

1. ECS 实例
2. 系统盘 / 数据盘
3. EIP
4. NAT Gateway
5. SNAT / DNAT 条目
6. 自定义镜像
7. 快照
8. 平台后续新增的其他计费资源

## 7. 本地数据模型设计

### 7.1 账单资源台账

新增一张本地“账单资源台账”，一条记录对应一个由平台创建且需要进入计费归属的云资源。

建议字段：

1. `id`
2. `cloudProvider`
3. `cloudAccountUid`
4. `regionId`
5. `cloudResourceId`
6. `cloudResourceType`
7. `billingScope`：`user | platform`
8. `ownerUserId`
9. `rangeInstanceId`
10. `singleInstanceBatchId`
11. `platformImageAssetId`
12. `sourceProvisionJobId`
13. `billingStartAt`
14. `releasedAt`
15. `tagsSnapshot`

17. `updatedAt`

约束建议：

1. `cloudProvider + cloudAccountUid + regionId + cloudResourceId + cloudResourceType` 需要唯一
2. `billingScope=user` 时，`ownerUserId` 必填
3. `billingScope=platform` 时，`ownerUserId` 为空

### 7.2 账单明细快照

新增“账单明细快照”表，一条记录对应一次从阿里云同步回来的账单明细行。

建议字段：

1. `id`
2. `syncBatchId`
3. `billCycle`
4. `billingDate`
5. `productCode`
6. `productDetail`
7. `billItem`
8. `cloudResourceId`
9. `cloudResourceType`
10. `pretaxAmount`
11. `currency`
12. `billingScope`
13. `ownerUserId`
14. `matchedLedgerId`
15. `rawPayload`
16. `createdAt`

约束建议：

1. 同一次同步批次内，同一笔账单明细不能重复写入
2. 命中台账后，需要固化 `ownerUserId` 和 `billingScope`，避免后续资源归属变化篡改历史账单

### 7.3 异常账单表

新增“异常账单”表，用于收口以下情况：

1. 账单资源看起来是平台资源，但无法命中本地台账
2. 账单资源标签不完整
3. 账单资源命中多个冲突归属

建议字段：

1. `id`
2. `syncBatchId`
3. `billCycle`
4. `billingDate`
5. `cloudResourceId`
6. `cloudResourceType`
7. `pretaxAmount`
8. `reason`
9. `rawPayload`
10. `createdAt`

## 8. 账单同步与归属流程

### 8.1 资源创建阶段

所有会产生计费资源的链路都必须补齐以下动作：

1. 创建云资源前构造统一标签
2. 云资源创建成功后，把云资源 ID 写入本地账单资源台账
3. 按资源归属写入：
   - `billingScope=user`
   - `billingScope=platform`
4. 与实例、批次、镜像资产、job 等现有业务主键建立关联

### 8.2 生命周期变化阶段

资源生命周期变化时，需要同步维护本地账单资源台账：

1. 销毁成功后更新 `releasedAt`
2. 二次打包镜像成功后新增镜像 / 快照台账
3. 删除镜像 / 快照成功后更新对应台账释放时间
4. 失败恢复时如果重新创建了新资源，需要新增新台账，而不是覆盖旧记录

### 8.3 账单同步阶段

平台增加定时任务 `billing-sync`，流程如下：

1. 拉取指定时间范围内的阿里云真实账单明细
2. 先按 `cloudResourceId` 命中本地账单资源台账
3. 对无法直接按资源 ID 命中的聚合型账单，走聚合归属规则
4. 命中后写入账单明细快照，并固化 `ownerUserId` 与 `billingScope`
5. 未命中或命中异常时写入异常账单表

### 8.4 聚合型账单处理

当前账单里已经出现两类不能稳定按单个资源 ID 直接命中的费用：

1. 快照链容量：账单维度可能只到地域，而不是单个快照 ID
2. 后续若平台接入专用 OSS 存储，容量 / 外网流量账单维度可能只到桶或存储类型，而不是平台业务对象

因此平台需要补一层聚合归属规则：

1. **资源 ID 直连优先**：能按 `cloudResourceId` 命中的费用直接按台账归属
2. **聚合存储边界次之**：对快照、镜像存储这类费用，要求平台使用可隔离的归属边界；若后续接入 OSS，同样适用，例如：
   - 专用平台桶
   - 专用对象前缀
   - 专用资源组
   - 本地存储台账
3. **无法隔离就不认用户账**：如果某类聚合型账单来自共享存储且无法稳定切分，只能：
   - 先归到平台公共费用
   - 或直接记为异常账单

聚合型账单不能靠“猜哪个用户大概用了多少”来分摊。

### 8.5 同步窗口策略

考虑阿里云账单存在延迟和修正，默认策略建议为：

1. 定时任务每次增量回补最近 7 天
2. admin 支持手动触发最近 30 天重刷
3. 首次上线时可做一次自 `2026-07-16` 起的历史回补

这样比“只同步昨天一次”更稳，也更适合账单晚到和修正场景。

## 9. 资源覆盖范围与现有链路改造

### 9.1 首期必须覆盖的费用类型

首期必须覆盖以下资源和成本：

1. ECS 实例计算费用
2. 系统盘 / 数据盘费用
3. 公网相关费用：EIP、带宽、流量
4. NAT 相关费用：NAT Gateway、SNAT、DNAT
5. 镜像与存储费用：自定义镜像、快照、镜像衍生存储

### 9.2 现有链路必须补账单标签和台账的区域

从当前仓库结构看，至少以下区域需要补齐：

1. 编排实例创建 / 销毁链路
2. 单实例创建 / 批量销毁链路
3. `pack-image` / 自定义镜像沉淀链路
4. OpenTofu 资源输出 `resourceSummary` 写回链路
5. worker 内部的失败恢复与替换资源链路

### 9.3 设计原则

本次不要求平台先知道所有阿里云计费科目细节，再反向设计页面；而是要求：

1. 平台所有会产生成本的资源链路都要进入“创建即打标、成功即建账单资源台账”的统一模型
2. 账单同步只负责回收真实金额，不负责猜归属
3. 对聚合型存储账单，必须先建立隔离边界或本地聚合台账，再允许进入用户账单

## 11. API 设计

接口保持现有 admin 风格，建议如下：

1. `GET /admin/billing/summary`
   - 入参：`startAt`、`endAt`
   - 返回：平台总应付、平台公共费用、按资源类型汇总、按天趋势、异常账单数
2. `GET /admin/billing/users`
   - 入参：`startAt`、`endAt`、分页
   - 返回：用户账单列表
3. `GET /admin/billing/users/:userId`
   - 入参：`startAt`、`endAt`
   - 返回：单用户账单概览
4. `GET /admin/billing/users/:userId/items`
   - 入参：`startAt`、`endAt`、分页、资源类型筛选
   - 返回：用户资源级账单明细
5. `GET /admin/billing/anomalies`
   - 入参：`startAt`、`endAt`
   - 返回：异常账单列表

### 11.1 导出接口

首期直接做同步下载，避免引入复杂异步导出队列。

建议接口：

1. `GET /admin/billing/export/platform.csv`
2. `GET /admin/billing/export/users.csv`
3. `GET /admin/billing/export/users/:userId.csv`

如果后续确实需要更重的导出格式，再补异步任务或对象存储导出。

## 12. 实现策略

### 12.1 第一阶段：先打通资源归属

先完成以下内容：

1. 统一账单标签规范
2. 所有新增计费资源创建成功后写入本地账单资源台账
3. 覆盖 ECS、磁盘、EIP、NAT、镜像 / 快照等主资源

### 12.2 第二阶段：再打通真实账单同步

完成以下内容：

1. 接入阿里云真实账单拉取
2. 写入账单明细快照
3. 写入异常账单
4. 提供最近 7 天自动回补与最近 30 天手动重刷

### 12.3 第三阶段：最后做后台展示与导出

完成以下内容：

1. 左侧导航
2. 平台总账单页
3. 用户账单列表
4. 用户账单明细
5. 异常账单页
6. CSV / Excel 导出

这样可以保证即使页面尚未全部完工，账单数据也已经开始积累，不会丢失首期上线后的费用归属信息。

4. `billingScope=platform` 的资源一定只进入平台总账单

### 13.3 资源覆盖验收

至少验证以下资源类型能出现在账单明细中：

1. ECS
2. 磁盘
3. EIP / 流量 / 带宽
4. NAT / SNAT / DNAT
5. 镜像 / 快照

### 13.4 异常验收

必须验证：

1. 当账单出现平台标签资源但无法归属时，会生成异常账单记录
2. admin 能在后台看到异常数量和异常明细
3. 导出结果中能附带异常账单数据或单独导出异常表
4. 对快照链容量这类聚合型账单，要么命中聚合归属规则，要么进入异常 / 平台公共费用，不能静默丢失

### 13.5 容器态验收

按仓库约束，凡涉及前端、后端、worker 或 OpenTofu 行为改动，交付前都必须：

1. 更新相关容器镜像
2. 在 Docker 容器态完成启动与验证
3. 不使用本地开发进程替代容器验证

## 14. 风险与后续关注点

本设计收口主线后，仍需继续关注以下事项：

1. 阿里云账单存在延迟和修正，平台必须接受“近几天数据会回补”的现实
2. 少数云资源如果在创建后被外部系统改标签，仍可能导致对账复杂化，因此本地台账比云上标签更重要
3. 快照链容量等聚合型账单天然不如 ECS / EIP 那样容易按资源 ID 追踪，必须提前设计隔离边界
4. 平台未来若引入更多计费资源，必须先补资源台账接入，再谈账单展示
5. 如果平台未来接入专用 OSS 桶或前缀，再把 OSS 计费接回本模型；共享 OSS 费用不进入当前 v1
6. 平台公共费用当前不分摊给用户；如以后需要分摊，应作为独立设计处理
