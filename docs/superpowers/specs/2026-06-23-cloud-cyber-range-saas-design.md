# 阿里云综合靶场竞赛平台设计文档

- 日期：2026-06-23
- 阶段：Brainstorming 设计确认稿
- 项目定位：阿里云综合靶场竞赛平台第一阶段 PoC

## 1. 设计结论

第一阶段不做完整 SaaS，也不做完整 CTF 平台，而是聚焦一个可运行、可演示、可扩展的云靶场编排内核。

第一阶段定义为：

> 一个由管理员操作的、面向比赛队伍的一键式阿里云综合靶场编排平台原型。

核心闭环为：

`创建比赛 -> 创建队伍 -> 选择靶场模板 -> 为队伍创建独立靶场 -> 平台返回访问入口与状态 -> 比赛结束后销毁资源`

## 2. 已确认的范围边界

### 2.1 第一阶段范围

- 单租户运营后台
- 管理员后台优先
- 云靶场优先
- PoC/原型验证优先
- 每个队伍拥有一套独立靶场
- 每套靶场对应一个独立 VPC
- 第一版靶场先支持纯 ECS 多机综合靶场
- 后续预留扩展到混合云资源靶场，如 `RDS / OSS / SLB / ACK`

### 2.2 第一阶段不做

- 多租户组织体系
- 完整选手前台
- 报名、支付、计费、套餐、配额
- 题目系统、Flag 判题、积分榜
- 在线拖拽式靶场设计器
- 真正可切换的多云执行能力
- 重型微服务拆分

## 3. 为什么不是直接二开现有平台

第一阶段建议采用“自研单体平台内核，只借鉴成熟平台经验”的路线。

### 3.1 借鉴对象

- `GZCTF`：借鉴后台组织方式、比赛/队伍/实例的产品经验，不直接复用其容器题运行时模型
- `CTFd`：借鉴后台对象管理与管理台信息架构
- `Haaukins`：借鉴事件、队伍、环境生命周期思路
- `GOAD`：借鉴靶场模板、环境内容组织与镜像策略

### 3.2 不直接作为底座的原因

现有开源 CTF 平台大多围绕题目系统、动态容器、Kubernetes 或传统竞赛流程设计，不是围绕“每队伍一套 VPC 级综合渗透靶场”设计。若直接继承其技术底座，后续会持续与原始模型冲突。

因此第一阶段结论是：

- 产品结构借鉴成熟平台
- 云靶场编排内核从头设计

## 4. 云资源与编排策略

### 4.1 靶场隔离策略

第一阶段采用：

- `每队伍 1 套独立靶场`
- `每套靶场 1 个独立 VPC`

这样做的收益：

- 队伍之间网络隔离明确
- 生命周期边界清晰
- 销毁回收简单
- 后续审计、连接、扩展更容易

关于 CIDR：

- 如果 VPC 永远完全隔离，CIDR 可以复用
- 但平台仍建议维护一个 `CIDR 池`
- 原因是后续可能接入堡垒机、日志采集、运维跳板、云企业网或统一监控，提前规避地址冲突更稳妥

### 4.2 编排架构

第一阶段采用：

`平台自研编排层 + OpenTofu/Terraform 作为底层 IaC 执行引擎`

推荐优先选用 `OpenTofu`，原因：

- 基本兼容 Terraform 配置与生态
- 更适合作为长期可控底座
- 多云扩展能力成熟
- 阿里云资源可通过现有 Provider 管理

平台侧不直接把 IaC 暴露给业务层，而是抽象成统一执行器。

### 4.3 相关工具分工

- `OpenTofu`：基础设施声明与创建/销毁
- `Packer`：预制靶机镜像
- `cloud-init`：实例首次启动时的轻量初始化
- `Ansible`：仅在确有需要时补充主机内配置管理

第一阶段不建议：

- 直接用阿里云 SDK/API 取代 IaC 作为主执行方式
- 把阿里云 ROS 作为平台主抽象

原因不是这些工具不能用，而是第一阶段更需要一致性、模板化和后续多云扩展空间。

## 5. 总体架构

第一阶段采用 `模块化单体`。

不是微服务，但内部边界从一开始就明确，为后续拆分预留空间。

### 5.1 模块划分

#### 1. Admin Web

管理员后台，负责比赛、队伍、靶场模板、环境实例、任务状态、审计信息展示与操作。

#### 2. Platform API

统一后端入口，负责认证、参数校验、业务对象管理，以及将“创建靶场/销毁靶场”转成异步任务。

#### 3. Provision Orchestrator

平台核心模块。维护任务状态机与步骤执行流程，不直接关心具体页面和前端。

#### 4. IaC Runner

封装 `tofu/terraform init/plan/apply/output/destroy` 执行逻辑，采集输出、状态、日志，并回传给平台。

#### 5. Template Registry

管理靶场模板元数据。第一版不做复杂模板市场，只管理模板标识、版本、变量定义、输出定义、默认策略。

#### 6. Image Pipeline

负责靶机镜像生产与版本管理。虽然不直接位于主业务请求路径上，但必须存在。

### 5.2 架构原则

- 同一仓库内实现前后端与编排模块
- API 层不直接执行云资源创建
- 所有创建与销毁行为都进入任务系统
- 模板与运行实例分离
- 业务层只认识环境实例，不直接感知底层 IaC 细节

## 6. 核心数据模型

第一阶段只保留最小但清晰的 6 个核心对象。

### 6.1 Competition

表示一次比赛或演练活动。

建议字段：

- `id`
- `name`
- `description`
- `status`
- `start_at`
- `end_at`
- `default_template_id`

### 6.2 Team

表示参赛队伍。

建议字段：

- `id`
- `competition_id`
- `name`
- `contact_name`
- `contact_email_or_phone`
- `notes`

### 6.3 RangeTemplate

表示靶场模板，是某类综合靶场的定义，而不是某次实际创建的资源。

建议字段：

- `id`
- `name`
- `slug`
- `version`
- `cloud_provider`
- `iac_type`
- `module_path_or_ref`
- `variable_schema`
- `output_schema`
- `default_network_policy`

### 6.4 RangeInstance

表示某个队伍实际拥有的一套靶场实例。

建议字段：

- `id`
- `competition_id`
- `team_id`
- `template_id`
- `status`
- `allocated_cidr`
- `cloud_provider`
- `access_entry`
- `resource_summary`
- `expires_at`
- `last_job_id`

### 6.5 ProvisionJob

表示一次异步执行任务，例如创建、销毁、重试、刷新状态。

建议字段：

- `id`
- `range_instance_id`
- `job_type`
- `status`
- `triggered_by`
- `started_at`
- `finished_at`
- `retry_count`
- `error_summary`

### 6.6 ProvisionJobStepLog

表示任务执行过程中的步骤级日志。

建议字段：

- `id`
- `job_id`
- `step_name`
- `status`
- `message`
- `stdout_excerpt`
- `stderr_excerpt`
- `started_at`
- `finished_at`

## 7. 任务状态机与主流程

### 7.1 RangeInstance 状态建议

- `draft`
- `pending_create`
- `creating`
- `running`
- `create_failed`
- `pending_destroy`
- `destroying`
- `destroy_failed`
- `destroyed`

### 7.2 ProvisionJob 状态建议

- `pending`
- `running`
- `succeeded`
- `failed`
- `cancelled`

### 7.3 创建靶场主链路

`管理员创建比赛`
-> `管理员录入队伍`
-> `管理员选择靶场模板`
-> `平台创建 RangeInstance`
-> `平台生成 ProvisionJob(create)`
-> `Orchestrator 执行预校验`
-> `分配 CIDR`
-> `渲染 IaC 变量`
-> `IaC Runner 执行 apply`
-> `读取 outputs`
-> `回写 RangeInstance`
-> `状态变为 running`

### 7.4 销毁靶场主链路

`管理员触发销毁`
-> `平台生成 ProvisionJob(destroy)`
-> `Orchestrator 校验当前状态`
-> `IaC Runner 执行 destroy`
-> `记录回收结果`
-> `RangeInstance 标记为 destroyed 或 destroy_failed`

## 8. 第一阶段功能清单

### 8.1 必做功能

### 1. 管理员登录

第一版可只支持单管理员账号或极简管理员账户体系，重点是保护后台入口。

### 2. 比赛管理

- 创建比赛
- 编辑比赛
- 设置时间范围
- 选择默认靶场模板

### 3. 队伍管理

- 手工创建队伍
- 批量导入队伍
- 查看队伍对应的环境状态

### 4. 靶场模板管理

- 管理模板元数据
- 绑定代码仓库中的 IaC module
- 查看模板版本与变量说明

### 5. 环境实例与任务管理

- 查看每个队伍的靶场实例
- 手动创建靶场
- 手动销毁靶场
- 失败后重试
- 查看任务步骤日志与输出摘要

### 8.2 不做的功能

- 选手注册/登录/报名
- 队伍成员体系
- 题目与 Flag 体系
- 公告、通知、积分榜
- 多租户权限管理
- 计费、配额、套餐
- 在线可视化模板编排器

## 9. 开发优先级

第一阶段不建议按页面顺序开发，而建议按“最短闭环”开发。

### Phase 1

- 定义 `RangeTemplate / RangeInstance / ProvisionJob`
- 准备最小阿里云靶场模板
- 跑通最小 IaC 执行器

### Phase 2

- 打通创建靶场任务链路
- 打通销毁靶场任务链路
- 回写实例状态与输出

### Phase 3

- 补充管理员后台页面
- 补充任务日志与失败可视化
- 补充过期回收与异常实例视图

### Phase 4

- 稳定性增强
- 模板版本化
- 镜像流水线收敛

## 10. 推荐技术栈

为了适配 solo 开发与第一阶段 PoC，推荐如下：

- `前端`：Next.js + React + TypeScript
- `后端`：NestJS
- `数据库`：PostgreSQL
- `ORM`：Prisma
- `任务执行`：PostgreSQL 驱动的应用内 Job Worker
- `IaC`：OpenTofu
- `镜像构建`：Packer
- `初始化`：cloud-init
- `部署`：Docker Compose

### 10.1 为什么不第一版上 Redis / MQ / 微服务

因为第一版重点不是大规模并发，而是：

- 编排逻辑正确
- 任务状态可追踪
- 失败可定位
- 资源可回收

数据库驱动 Worker 更简单、易部署、易调试，更适合第一版。

## 11. 视觉系统与产品表达

第一阶段视觉方向已确认：

- `整体气质`：专业 SaaS 控制台
- `产品呈现`：轻官网 + 强后台

### 11.1 视觉原则

- 可信、克制、专业
- 更像云安全基础设施平台，不像活动页
- 不采用大面积黑红炫技风
- 让用户一眼看到“靶场生命周期”和“云资源状态”

### 11.2 色彩与风格

- 主色：深青绿
- 辅色：冷灰、米白
- 状态色：低饱和红橙作为告警/异常
- 风格：卡片分区清晰、留白充足、少量可视化点缀

### 11.3 后台结构建议

- 左侧主导航
- 顶部全局状态区
- 主内容区以表格、状态卡、日志面板为核心

重点页面：

- `比赛列表`
- `队伍列表`
- `靶场模板`
- `环境实例`
- `任务中心`
- `审计日志`

### 11.4 官网结构建议

第一版只做克制的一页式官网：

- Hero
- 核心能力
- 靶场编排流程图
- 产品截图
- 登录入口

## 12. 安全边界

即使是单租户 PoC，也应从第一版立住以下边界：

- 阿里云凭据只保存在服务端安全配置中
- 日志中不明文输出靶机敏感凭据
- 管理员关键操作进入审计日志
- 模板执行目录、输出文件、状态文件有明确隔离规范

## 13. 错误处理与异常收敛

第一阶段重点关注 4 类错误：

### 13.1 参数或模板错误

例如变量缺失、CIDR 冲突、镜像缺失。应尽量在执行 `apply` 前阻断。

### 13.2 IaC 执行错误

应保存：

- 退出码
- 标准输出摘要
- 错误输出摘要
- 执行时长

### 13.3 云侧部分成功

例如 VPC 已建成但 ECS 未完全创建。平台必须：

- 不把实例显示为成功
- 记录残留资源
- 允许管理员重试或销毁

### 13.4 回收失败

销毁失败必须有单独视图，便于控制云资源成本与遗留风险。

## 14. 运维策略

第一阶段采用“半自动可干预”策略：

- 平台自动创建
- 平台自动销毁
- 管理员可手动重试
- 管理员可手动标记异常实例
- 管理员可查看任务日志和输出摘要

这比一开始追求复杂自动补偿更适合 PoC 阶段。

## 15. 测试策略

第一阶段测试围绕最贵、最容易出事的链路展开。

### 15.1 单元测试

覆盖：

- 任务状态流转
- 参数校验
- CIDR 分配
- 模板变量渲染

### 15.2 集成测试

覆盖：

- API 创建任务
- Worker 消费任务
- 状态回写与日志记录

### 15.3 真实云验证

准备最小阿里云模板，反复验证：

`创建 VPC -> 创建 1 台 ECS -> 获取输出 -> 销毁`

这是第一阶段最重要的真实闭环测试。

### 15.4 回归清单

每次关键改动后至少手工验证：

- 创建成功
- 创建失败时状态正确
- 销毁成功
- 销毁失败可见
- 重复点击不会重复创建

## 16. 第一阶段完成标准

当以下能力都具备时，可认为第一阶段 PoC 达成：

- 管理员可创建比赛与队伍
- 管理员可选择模板并为队伍创建靶场
- 平台可为每队伍创建独立 VPC + 多台 ECS
- 平台可展示实例状态、访问入口与任务日志
- 平台可销毁靶场并处理失败状态
- 整套流程可在一个真实阿里云测试环境中反复验证

## 17. 下一步

本设计确认后，下一阶段应进入实现计划，不直接开始编码细节发散。

推荐的下一个产物是：

- 一份按模块与里程碑拆解的 implementation plan
- 明确每个阶段的交付物、依赖关系和验证方式
