# 阿里云综合靶场竞赛平台设计文档

- 日期：2026-06-23
- 状态：当前有效设计基线
- 适用阶段：第一阶段 PoC / 管理后台优先 / 阿里云优先
- 说明：本版本已取代早期“single-ecs bootstrap + CIDR 池优先”的设计假设

## 1. 设计结论

第一阶段的平台定位，不是通用云实验平台，也不是传统题目型 CTF 平台，而是：

> 面向网络安全竞赛与演练场景的阿里云综合靶场编排平台。

平台要解决的核心问题是：

- 管理员如何为不同队伍快速创建一整套独立、可公网进入、可销毁的企业网络型靶场
- 平台如何稳定记录这套靶场的状态、入口信息、任务过程与失败原因

第一阶段最小闭环为：

`创建比赛 -> 创建队伍 -> 选择靶场模板 -> 为该队伍创建一整套独立靶场 -> 返回公网入口与任务日志 -> 比赛结束后整套销毁`

## 2. 范围边界

### 2.1 第一阶段必须做

- 单租户管理员后台
- `Competition / Team / RangeTemplate / RangeInstance / ProvisionJob / ProvisionJobStepLog`
- 阿里云靶场模板管理
- 一队一套独立靶场实例
- 一套靶场独享一个 VPC
- 单 VPC 下的多网络区 / 多子网 / 多 ECS 企业网络拓扑
- 至少 1 台承担公网入口的 DMZ/边界 ECS，直接绑定独立 EIP
- 创建、销毁、状态回写、步骤日志、失败摘要

### 2.2 第一阶段明确不做

- 多租户组织体系
- 用户前台、报名、支付、套餐、计费
- 题目系统、Flag 判题、积分榜
- 拖拽式靶场设计器
- 完整多云抽象层
- 高级 CIDR 池编排
- 大规模自动补偿与复杂调度系统

### 2.3 第一阶段保留扩展位

- 混合云资源靶场
- `RDS / OSS / SLB / ACK` 等非 ECS 资源
- NAT Gateway + `SNAT / DNAT`
- 统一日志采集、运维跳板、云企业网互联

## 3. 为什么不直接二开现有开源平台

建议继续采用“自研平台内核，只借鉴成熟平台经验”的路线。

可借鉴对象：

- `GZCTF`：后台对象组织、比赛与队伍管理方式
- `CTFd`：后台信息架构与管理操作体验
- `Haaukins`：事件、队伍、环境生命周期的产品思路
- `GOAD`：企业网络型靶场内容组织和镜像策略

不直接把它们作为底座的原因是：

- 现有平台多围绕题目系统、容器题、Kubernetes、传统比赛流程设计
- 你的场景核心不是“给队伍分一组题容器”，而是“给队伍复制一整套企业网络靶场”
- 如果直接沿用它们的运行时假设，后续会持续与 `一队一套 VPC 级综合靶场` 的模型冲突

结论：

- 产品组织和后台交互可以借鉴成熟平台
- 云靶场模板、实例、编排、入口模型必须自研

## 4. 核心业务约束

这些约束是当前最高优先级，不允许在实现时被弱化。

### 4.1 一队一套独立靶场

- 一个队伍对应一套独立靶场实例
- 不允许多个队伍共享同一套靶场资源
- 生命周期以“整套靶场”为单位，不以单台主机为单位

### 4.2 一套靶场独享一个 VPC

- 每个 `RangeInstance` 独享一个 VPC
- 销毁时按整套 VPC 及其子资源统一回收
- 这样做的目标是网络隔离、生命周期隔离、回收边界清晰

### 4.3 模板定义固定拓扑

- 实例化时复制的是固定蓝图，不是运行时随意拼装
- 模板需稳定表达网络区、主机角色、连通关系和访问入口
- 第一阶段不做自由拖拽式拓扑编辑

### 4.4 模板需表达固定私网地址规划

- 靶机私网 IP 是模板设计的一部分
- 平台运行时不应随机给靶机生成内部 IP
- 第一阶段重点是“复制固定企业网络拓扑”，不是“在线拼地址”

### 4.5 公网入口按队伍隔离

- 每个队伍通过各自的公网入口访问自己的靶场
- 不允许多个队伍共享一个公网入口后再靠平台逻辑区分

## 5. 靶场拓扑模型

每个靶场实例不是单台主机，而是一套企业网络副本。

第一阶段默认拓扑至少应支持：

- 1 个独立 VPC
- 多个网络区 / 子网
- 多台 ECS 靶机
- 至少 1 台 DMZ/边界入口 ECS

推荐的第一版网络区包括：

- `dmz`
- `office`
- `server`
- `database`

可选扩展区包括：

- `management`
- `logging`
- `domain`

第一阶段的实现重点不是覆盖所有区，而是先把“多区、多机、边界入口”这组能力做成稳定骨架。

## 6. 公网访问模型

### 6.1 第一阶段默认模型

- 每套靶场至少 1 台 DMZ/边界 ECS
- 该 ECS 绑定独立 EIP
- 队伍通过该公网 IP 进入靶场
- 其他内网主机默认不直接暴露公网

### 6.2 后续扩展模型

- DMZ ECS 兼任跳板机、反向代理或边界服务机
- NAT Gateway + `DNAT` 暴露特定内网服务
- NAT Gateway + `SNAT` 为内网主机提供主动出网

### 6.3 设计约束

- `SNAT` 解决内网主机主动访问公网
- `DNAT / EIP` 解决公网用户访问靶场入口
- 第一阶段必须把 `DMZ + EIP` 入口视为一等公民，而不是最后顺手返回一个 IP

## 7. 模板模型

`RangeTemplate` 不是“模块路径 + 少量变量”的薄封装，而是一套完整靶场蓝图。

第一阶段建议让模板至少表达以下信息：

### 7.1 基础信息

- `name`
- `slug`
- `version`
- `cloudProvider`
- `iacType`
- `moduleRef`

### 7.2 网络拓扑定义

- 需要哪些网络区 / 子网
- 每个网络区的用途
- 哪个网络区承担公网入口
- 区与区之间的设计关系

### 7.3 主机定义

- 主机名称
- 所属网络区
- 规格
- 镜像
- 固定私网 IP
- 角色标签，如 `entry / jump / dc / db / app`
- 是否需要公网暴露

### 7.4 访问入口定义

- 哪台主机承担公网入口
- 入口协议与端口
- 平台创建完成后如何返回给管理员和队伍

### 7.5 执行策略

- 是否需要 `SNAT`
- 是否需要 `DNAT`
- 是否需要安全组预置规则
- 是否需要 `cloud-init`
- 是否需要附加初始化脚本

### 7.6 第一阶段的数据落地建议

第一阶段不需要把模板过度规范化成很多张表，可以先把模板蓝图放在 JSON 结构中，但语义必须清晰。

建议方向：

- `RangeTemplate` 保留基础元数据字段
- 增加一个明确的 `blueprint` 或 `topologySpec` 结构保存网络区、主机、入口和执行策略
- `modulePathOrRef` 只表示 IaC 实现入口，不再代表完整模板本身

## 8. 实例模型

`RangeInstance` 表示某个队伍真正拥有的一整套靶场实例。

第一阶段它应重点回答的问题是：

- 这套固定拓扑是否成功创建
- 当前状态是什么
- 公网入口是什么
- 哪一步失败了
- 最近一次任务是什么

建议重点字段：

- `competitionId`
- `teamId`
- `templateId`
- `status`
- `accessEntry`
- `resourceSummary`
- `lastJobId`
- `expiresAt`
- `errorSummary`

其中：

- `accessEntry` 应明确保存公网入口 IP、入口机角色、协议、访问方式
- `resourceSummary` 应保存 VPC、子网、ECS、EIP 的摘要

关于 `allocatedCidr`：

- 不是第一阶段核心字段
- 如果每套模板内部地址固定、VPC 彼此不互联，可以先降级为可选能力
- 只有在后续要做统一运维、互联、日志采集时，它才会重新变重要

## 9. 编排与任务模型

第一阶段的执行闭环必须围绕任务系统展开。

### 9.1 ProvisionJob

用于记录：

- 创建任务
- 销毁任务
- 重试任务
- 状态刷新任务

### 9.2 ProvisionJobStepLog

用于记录步骤级执行过程，例如：

- `prepare`
- `render_template`
- `tofu_init`
- `tofu_plan`
- `tofu_apply`
- `collect_outputs`
- `persist_access_entry`
- `destroy`

### 9.3 状态回写原则

- API 层不直接创建云资源
- 所有创建与销毁都进入任务系统
- Worker/Orchestrator 负责状态机推进和步骤日志写入
- 后台展示状态、错误摘要、入口信息和步骤日志

## 10. 技术架构

第一阶段继续采用模块化单体。

### 10.1 模块划分

- `Admin Web`：管理员控制台
- `Platform API`：后台 API 与认证、校验、对象管理
- `Provision Orchestrator`：创建/销毁状态机与任务执行流程
- `IaC Runner`：封装 OpenTofu 执行和输出采集
- `Template Registry`：模板元数据和蓝图管理
- `Image Pipeline`：镜像版本与初始化资产管理

### 10.2 架构原则

- 同仓开发，边界清晰
- 编排与 UI 分离
- 模板与实例分离
- 业务层只感知模板和实例，不直接操作底层 CLI

## 11. IaC 与工具决策

### 11.1 OpenTofu 作为第一阶段主执行引擎

选择原因：

- 与 Terraform 生态兼容
- 更适合作为可控底座
- 后续多云和混合云扩展成本较低
- 阿里云已有可用 Provider

### 11.2 其他工具分工

- `Packer`：预制靶机镜像
- `cloud-init`：实例首次启动初始化
- `Ansible`：只在确有需要时补主机内复杂配置

### 11.3 多云与混合云策略

- 第一阶段执行面只做阿里云
- 但模板模型、Runner 边界、模块命名应避免把“单 ECS”写死在主抽象里
- 后续混合云扩展应建立在“蓝图 + Provider 模块”之上，而不是继续堆单机脚本

## 12. 对当前仓库的纠偏要求

当前仓库最需要尽快纠偏的点有三个。

### 12.1 IaC 模块过于简单

当前主模块仍是：

- `infra/opentofu/modules/alicloud-vpc-single-ecs`

这只适合作为早期 OpenTofu 通路验证，不再符合第一阶段真实目标。

下一步应升级为：

- `single-vpc + multi-vswitch + multi-ecs + dmz-eip`

### 12.2 模板表达能力不足

当前模板模型还不足以表达：

- 多网络区
- 多主机
- 固定私网 IP
- 入口机角色
- 访问入口定义

### 12.3 CIDR 池被放得过重

`allocatedCidr` 不应再作为当前主线的中心字段。

优先级应改为：

1. 固定拓扑模板
2. 多区多机企业网络骨架
3. DMZ EIP 入口
4. 状态与日志回写
5. CIDR 池等可选增强

## 13. 测试与验证策略

第一阶段验证分三层：

### 13.1 静态结构验证

- OpenTofu 模块目录结构
- 变量与 outputs 契约
- 示例 root module 可 `fmt` / `validate`

### 13.2 后端集成验证

- 创建比赛、队伍、模板、实例
- 任务创建与状态流转
- 步骤日志回写
- 访问入口和资源摘要回写

### 13.3 真实云验证

- 在阿里云侧创建一套真实企业网络型靶场
- 验证 DMZ EIP 可访问
- 验证销毁能回收整套资源

## 14. 后台与视觉方向

第一阶段继续坚持管理员后台优先。

产品表达应强调：

- 云上企业网络靶场
- 队伍独立环境
- 可观察的编排过程

UI 风格建议：

- 信息密度高但层级清楚
- 首页突出比赛、队伍、实例、任务四条主线
- 实例详情页突出公网入口、资源摘要、任务过程、异常摘要
- 后续详细设计可使用 `ui-ux-pro-max` 系列技能进一步扩展

## 15. 当前有效实现优先级

从现在开始，正确的执行顺序是：

1. 重写并固定企业网络型靶场设计与计划基线
2. 把 `single-ecs bootstrap` 升级为企业网络型 OpenTofu 骨架
3. 扩展 `RangeTemplate`，让它能表达拓扑蓝图
4. 扩展 `RangeInstance.accessEntry / resourceSummary`
5. 收口编排、步骤日志、状态回写
6. 最后再回到后台展示和可选增强

## 16. 第一阶段完成标准

第一阶段完成，不是指平台“看起来像 SaaS”，而是以下闭环真正跑通：

- 管理员创建比赛
- 管理员创建队伍
- 管理员选择模板
- 平台为该队伍创建一整套独立靶场
- 平台明确返回公网入口、状态和任务日志
- 比赛结束后平台销毁整套靶场

只要这个闭环稳定成立，第一阶段就是成功的。
