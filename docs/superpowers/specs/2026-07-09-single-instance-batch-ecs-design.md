# 单实例批次化与 ECS 原生执行设计

- 日期：2026-07-09
- 适用分支：`codex/platform-bootstrap`
- 相关页面：`/admin/instances`
- 目标范围：单实例管理（不改编排实例的 OpenTofu 主链）

## 背景

当前“实例管理”页面的单实例能力已经可用，但执行模型仍然沿用“逐条记录 + 逐条 job + worker 全局单线程”的方式：

1. 前端一次提交 `quantity = N` 时，后端会创建 `N` 条 `RangeInstance` 记录。
2. 每条记录单独创建 1 条 `ProvisionJob(create)`。
3. `ProvisioningWorkerService.runLoop()` 每次只认领 1 条 `pending` job 串行执行。
4. 单实例创建/销毁当前仍依赖 OpenTofu 单机链路。

这会带来三个直接问题：

- 批量创建很慢，`quantity > 1` 时本质是逐台串行创建。
- 一个实例销毁未完成时，新的单实例创建会排队等待。
- 多个实例关闭/回收时，用户期望并行，但系统当前表现为串行。

同时，用户已经明确给出以下产品方向：

- 单实例应优先使用阿里云 ECS 原生能力，而不是继续调用 OpenTofu。
- 批量创建要从前端表现为“1 个批次记录”，可以展开看到多台子实例。
- 子实例仍然保留单独关闭、重启、打包、VNC 等能力。
- 批次主行需要提供“一键关闭”。
- “关闭实例”的产品语义为“回收/销毁 ECS，并进入历史”，不是传统意义上的 stop 后可恢复。
- 当前部署目标是一台 2h4g 服务器，因此并发必须受控。

## 目标

本次改造只覆盖“单实例管理”，目标是：

1. 单实例创建/回收切换为 ECS 原生接口。
2. 将前端批量创建建模为“批次主行 + 可展开子实例表格”。
3. 子实例执行保留现有单机操作能力。
4. 批次创建与批次回收支持并行，受控并发上限先定为 3。
5. 编排实例（range mode）继续保持现有 OpenTofu 执行链路不变。

## 非目标

以下内容本次不做：

- 不重构编排实例 worker 调度模型。
- 不将整个 provisioning 系统抽象为统一的大型任务调度中心。
- 不引入批次级“重试全部失败项”入口。
- 不新增全新的实例详情页面或抽屉视图。
- 不把单实例历史页重做为独立批次历史模块之外的全新交互。

## 当前数据流

当前单实例的主要数据流如下：

1. `SingleInstancesService.launch()`：
   - 确保默认单实例网络存在。
   - 读取启用的平台镜像。
   - 为 `quantity` 内的每一台实例生成：
     - `runtimeTopologyGraph`
     - `runtimeScenarioTemplateSpec`
     - `runtimeCompiledProvisionSpec`
     - `runtimeCredentials`
     - `singleInstanceConfig`
   - 写入 1 条 `RangeInstance`
   - 写入 1 条 `ProvisionJob(create)`

2. `ProvisioningWorkerService.runLoop()`：
   - 从所有 `pending` jobs 中只取 1 条。
   - 如果 `instanceMode === 'single'`，走 `processSingleInstanceJob()`。
   - 单实例路径最终仍通过 `OpenTofuRangeProvisioner` 及单实例 module 落地 ECS。

3. 执行结果回写：
   - `accessEntry`
   - `resourceSummary`
   - `status`
   - `errorSummary`

问题不在“前端 quantity 输入”，而在于后端没有把 quantity 视作一个批次任务，而是把它展开成了多个串行实例任务。

## 设计方案

### 方案选择

本次采用：

- **批次主行 + 展开子实例表格**
- **单实例 ECS 原生批量创建/回收**
- **单实例路径受控并发 = 3**
- **编排实例 OpenTofu 路径保持不动**

不采用：

- 全平台通用多类型任务调度器
- 单实例继续走 OpenTofu 但只提高 worker 并发
- 主表只显示批次、子实例通过抽屉/详情页查看

### 前端表现

实例管理列表将支持两种行类型：

1. **普通单实例行**
   - 兼容当前已经存在的历史数据或迁移期数据。

2. **批次行**
   - 作为主表中的一条记录展示。
   - 点击展开后，显示该批次下的子实例表格。

批次主行展示字段：

- 展开/收起控件
- 批次名
- 镜像
- 数量
- 状态汇总
- 创建时间
- 到期时间
- 创建人
- 操作（一键关闭 / 更多）

展开后的子表格展示字段：

- 子实例名
- 规格
- 公网 IP
- 账号/密码
- 状态
- 操作（关闭 / 重启 / 打包 / VNC）

实例历史页沿用相同结构：

- 历史页主行展示“已关闭的批次”。
- 展开后查看子实例历史明细。
- 历史页不保留“操作”列。

### 批次状态策略

本次不引入复杂的批次状态枚举作为唯一事实来源，而是优先采用**子实例状态聚合**来生成批次展示状态。

批次主行示例：

- `5 创建中`
- `3 运行中 / 2 创建中`
- `4 运行中 / 1 创建失败`
- `2 销毁中 / 3 已关闭`
- `5 已关闭`

这样做的原因：

- 避免批次状态与子实例状态之间的双写一致性问题。
- 更符合运维视角。
- 更适合展示部分成功/部分失败场景。

可选实现：

- 查询时现算（首选）
- 子实例状态更新时顺手回写汇总快照（后续可做）

本次先采用**查询时现算**。

## 数据模型

### 新增批次实体

新增单实例批次实体，例如 `SingleInstanceBatch`，字段如下：

- `id`
- `name`
- `platformImageAssetId`
- `imageId`
- `imageDisplayName`
- `cpu`
- `memory`
- `systemDiskSize`
- `expiresAt`
- `quantity`
- `remark`
- `createdBy`
- `statusSummary`（可选，首期不作为事实主源）
- `createdAt`
- `updatedAt`

### 子实例继续沿用 `RangeInstance`

现有 `RangeInstance` 保持为单台 ECS 的事实记录，仅新增与批次关联的字段，例如：

- `singleInstanceBatchId?: string | null`

保留现有单实例字段：

- `instanceMode = 'single'`
- `singleInstanceConfig`
- `runtimeCredentials`
- `accessEntry`
- `resourceSummary`
- `status`
- `errorSummary`

这样可最大化复用现有：

- 单实例状态展示
- VNC
- 打包镜像
- 账号/密码显示
- 历史能力

### `SingleInstanceConfig` 调整

`SingleInstanceConfig` 当前主要承载单机展示和网络信息。迁移到 ECS 原生接口后，建议调整为：

- 保留：
  - `baseName`
  - `quantityIndex`
  - `hostKey`
  - `hostName`
  - `platformImageAssetId`
  - `imageId`
  - `imageDisplayName`
  - `cpu`
  - `memory`
  - `systemDiskSize`
  - `remark`
  - `assignedVswitchId`
- 弱化/删除对预分配私网 IP 的依赖

## 执行模型

### 单实例创建

批量创建不再交给 OpenTofu worker，而改为：

1. 确保默认单实例网络存在。
2. 创建 1 条批次记录。
3. 根据 `quantity` 创建 `N` 条子实例 `RangeInstance` 记录，绑定到该批次。
4. 使用阿里云 ECS 原生批量创建接口：
   - `RunInstances`
5. 接收返回的 ECS 实例标识，并将结果映射回子实例记录。
6. 轮询这些实例的创建结果与可见状态，回写：
   - ECS 实例 ID
   - 公网 IP / 私网 IP
   - `running / create_failed`
   - 失败原因

### 单实例回收

“关闭实例”的产品语义定义为“回收/销毁 ECS 实例”。

批量回收：

1. 选择一个批次主行。
2. 找出所有未销毁的子实例。
3. 使用阿里云原生批量回收能力：
   - 优先 `DeleteInstances`
4. 对成功/失败项分别写回状态：
   - `destroyed`
   - `destroy_failed`

单机关闭：

- 子实例级别的关闭仍然可保留，走同一类回收逻辑，但只针对该子实例。

### 单实例重启

子实例重启改走 ECS 原生接口：

- 单机：`RebootInstance`
- 批量：暂不提供批次级重启入口

### VNC

子实例 VNC 继续走现有 ECS VNC 链路：

- 原始 `VncUrl`
- 组装后的 `webTerminalUrl`

批次主行不直接提供 VNC，VNC 只在子实例层级暴露。

## 并发策略

### 用户确认的约束

部署目标为一台 `2h4g` 服务器，因此不采用“全平台无约束并发”。

### 本次并发设计

本次先将并发控制限定在“单实例 ECS 原生执行路径”，并发上限为 **3**。

解释如下：

- 不是“3 个 OpenTofu apply 并行”
- 不是“整个平台所有任务都 3 并发”
- 而是“最多 3 个单实例批次级执行任务同时推进”

一个批次任务可能是：

- 批量创建
- 批量回收

这样做的好处：

- 直接解决单实例场景的用户痛点
- 不把编排实例的重型 OpenTofu 路径一起卷入改造
- 在 2h4g 机器上更稳

### 同实例互斥

必须保留实例级互斥约束：

- 同一个子实例不能并发执行两条状态变更任务
- 例如不能同时“关闭 + 重启”

VNC 不修改实例状态，可视为读操作，不参与状态互斥。

### 编排实例保持不变

编排实例暂不接入这次的 3 并发单实例池。

也就是说：

- 单实例批次路径：新执行模型
- 编排实例路径：沿用当前 OpenTofu worker 模型

## 网络与规格处理

### 默认网络

单实例仍复用现在的持久化默认网络：

- 1 个默认 VPC
- 该 VPC 下的 3 个交换机
- 1 个默认安全组（全开放）

这部分现有 bootstrap 能力保留，不重做。

### 私网 IP

用户已经明确说明：

- 内网 IP 无所谓，系统自动分配

因此本次不再以“自定义预分配私网 IP”为主路径。

优先策略：

- 由阿里云在选定交换机内自动分配私网 IP

这能显著减少并发创建时的冲突面和本地分配逻辑复杂度。

### 规格

规格校验仍保留当前平台已有规则：

- CPU / 内存来自前端输入
- 使用现有规格可售性校验接口
- 经济型规格优先策略继续保留

ECS 原生批量创建时需要确保：

- 规格校验在批量请求前已通过
- 如果某一批量请求仍因容量或售卖窗口失败，失败项要回写到子实例级别

## 错误处理

### 部分成功

批量创建和批量回收必须支持“部分成功”：

- 成功项进入目标状态
- 失败项进入失败状态并保留错误摘要
- 批次主行展示聚合结果

### 重试

首期保留**子实例级重试**：

- `create_failed` 子实例可以单独重试
- `destroy_failed` 子实例可以单独重试

首期不提供：

- 整批“重试全部失败项”

### 用户可见提示

前端需要把失败定位到可理解粒度：

- 批次主行显示汇总失败数量
- 展开后能看到具体失败的是哪些子实例
- 子实例行保留失败状态和后续可重试能力

## 兼容与迁移

### 旧数据兼容

现有单实例记录中已经存在不少“单机式 single instance”数据。

前端需要兼容两种数据形态：

1. 有 `batchId` 的新批次化子实例
2. 无 `batchId` 的旧单实例记录

兼容策略：

- 新前端列表页渲染时：
  - 有批次的按批次主行聚合显示
  - 无批次的按普通单实例行继续显示

### 后端迁移

迁移应包括：

- 新增批次表
- 子实例增加 `batchId`
- 相关索引与外键

不需要强行把所有旧单实例数据回填到批次表。

## API 设计方向

预计新增或调整以下接口语义：

- `POST /admin/instances/launch`
  - 从“返回多条普通单实例”演进为“创建批次 + 子实例”
- `GET /admin/instances`
  - 返回适合前端直接渲染的批次化列表结构，或返回平铺数据由前端聚合
- `POST /admin/instances/:batchId/destroy-all`
  - 新增批次级一键关闭
- 保留子实例级：
  - `destroy`
  - `retry`
  - `reboot`
  - `open-vnc`
  - `pack-image`

为了减少前端复杂度，推荐：

- 后端直接返回“批次 + 子实例”结构

## 测试与验证

### 自动化测试

至少覆盖：

1. 批量创建批次记录与子实例记录映射关系
2. 部分成功创建时的状态回写
3. 批量回收部分成功时的状态回写
4. 批次主行聚合查询
5. 子实例级单独操作在批次模式下仍可用
6. 刷新后前端仍能正确恢复展开/列表视图基础状态

### 容器态验证

按仓库要求，涉及前端 / 后端 / worker 行为改动后，需要：

- 更新相关容器镜像
- 在容器态完成验证

重点验证项：

- 创建 5 台实例的批次展示
- 一个批次回收时，另一个批次仍可创建
- 两个批次一键关闭可并行推进
- 子实例单独关闭 / 重启 / 打包 / VNC
- 历史页展示批次记录与子实例历史

## 风险

主要风险如下：

1. **批量 ECS 返回与子实例映射**
   - 需要保证返回结果准确匹配到本地子实例。

2. **部分成功状态一致性**
   - 不能把整批简单标成成功或失败。

3. **旧数据兼容**
   - 新前端必须兼容旧单实例记录。

4. **并发上限失控**
   - 2h4g 机器上必须严格把单实例执行并发限制在 3。

## 推荐实现顺序

1. 新增设计文档并确认
2. 写实现计划
3. 数据层迁移：批次表 + 关联字段
4. 单实例执行层切换到 ECS 原生接口
5. 单实例批次列表前端改造
6. 批次一键关闭
7. 容器态验证

## 推荐结论

本次最优路线不是“给现有 OpenTofu worker 简单加线程”，而是：

- **单实例场景彻底切到 ECS 原生接口**
- **前端引入批次主行 + 子实例展开表格**
- **单实例路径单独做受控并发 = 3**
- **编排实例路径维持现状**

这条路线最贴近用户诉求，也最符合当前部署资源约束。
