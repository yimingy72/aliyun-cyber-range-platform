# 阿里云综合靶场竞赛平台后台体验设计文档

- 日期：2026-06-24
- 状态：已完成设计确认，待按实现计划落地
- 关联基线文档：[2026-06-23-cloud-cyber-range-saas-design.md](./2026-06-23-cloud-cyber-range-saas-design.md)
- 适用阶段：第一阶段 PoC / 管理后台优先 / 中文界面优先

## 1. 设计目标

这一版设计解决的不是底层云编排逻辑，而是平台的第一层使用体验：

- 管理员如何看懂系统入口
- 管理员如何登录后台
- 登录后首先看到什么
- 后台应该围绕什么组织，而不是沦为一堆 CRUD 表单

本设计的目标是把当前前端收敛成一套像正式产品的管理后台，而不是开发调试页。

## 2. 本次设计结论

### 2.1 入口结构

第一阶段不做公共官网式首页。

最终入口策略为：

- `/`：直接重定向到 `/login`
- `/login`：普通用户/选手登录页
- `/admin/login`：管理员独立登录页
- `/admin`：管理员登录后的后台首页

这样处理的原因：

- 用户明确不需要公共首页
- 平台第一阶段核心不是品牌展示，而是尽快进入登录与运维工作流
- 保留选手和管理员双入口，但不增加额外跳转层级

### 2.2 后台产品定位

后台不是传统“比赛管理表格后台”，而是：

> 面向综合靶场编排与运维的控制台型后台

它的第一职责不是录入对象，而是回答：

- 现在有多少靶场在运行
- 哪些队伍的靶场创建失败了
- 最近一次编排任务卡在哪一步
- 每个实例的公网入口是什么

### 2.3 视觉方向

视觉方向采用已确认的 A 方案：`云控中枢`。

视觉原则：

- 管理后台使用蓝黑品牌色 + 浅色工作区
- 表现“企业级、可信、可运维”，避免廉价深色大屏感
- 页面重点放在状态、入口、任务与日志的层级清晰度
- 普通用户登录页与管理员登录页风格统一，但权限角色明确区分

### 2.4 语言策略

第一阶段前端界面统一使用中文。

包括但不限于：

- 页面标题
- 导航项
- 按钮文案
- 表格列名
- 状态提示
- 错误提示
- 空状态说明

保留的英文仅限：

- 资源字段值本身，如 `running`、`create_failed`
- 云资源标识，如 `vpc-xxxx`
- 技术日志原文

## 3. 路由与页面边界

### 3.1 第一阶段必须落地的页面

#### 1. `/login`

定位：普通用户/选手登录页。

本轮职责：

- 提供正式的选手登录入口页面
- 在视觉上与管理员登录页同属一个产品体系
- 提供跳转到管理员入口的明确文字链接

本轮不做：

- 选手中心
- 战队空间
- 积分榜
- 题目页
- 比赛大厅

它在第一阶段是正式入口页，但功能范围仍受控，不扩展为完整选手产品。

#### 2. `/admin/login`

定位：管理员独立登录页。

职责：

- 清晰表达“这是后台管理入口”
- 在登录页上展示平台一句话价值说明
- 提供账号密码登录动作
- 对错误凭据给出明确反馈

设计要求：

- 不在页面硬编码默认账号密码
- 不呈现“测试页”“开发页”的视觉感觉
- 左侧偏品牌与能力说明，右侧偏登录动作

#### 3. `/admin`

定位：管理员登录后的默认首页，即靶场总览。

职责：

- 成为登录后的第一屏
- 优先展示靶场和任务的总体运行情况
- 帮助管理员快速发现异常，而不是先进入配置编辑

建议第一屏内容：

- 运行中靶场数量
- 创建中任务数量
- 失败实例数量
- 最近可用公网入口数量或最近更新实例
- 最近任务列表
- 需要关注的异常实例

### 3.2 第一阶段应同步建立的后台二级路由

这些页面可以作为后台一级导航落地：

- `/admin`
- `/admin/range-instances`
- `/admin/provision-jobs`
- `/admin/settings`

其中：

- `/admin/settings` 内部再通过标签页或子导航切换 `比赛 / 队伍 / 模板 / 云配置`

不建议把 `比赛`、`队伍`、`模板` 直接提升为一级导航，原因是这会让后台退化成传统对象管理后台，弱化“靶场运维控制台”的主线。

## 4. 后台信息架构

### 4.1 一级导航

后台一级导航固定为：

- `靶场总览`
- `靶场实例`
- `编排任务`
- `基础配置`

对应关系：

- `靶场总览` -> `/admin`
- `靶场实例` -> `/admin/range-instances`
- `编排任务` -> `/admin/provision-jobs`
- `基础配置` -> `/admin/settings`

### 4.2 基础配置的组织方式

`基础配置` 页面内使用页内标签页或二级分段切换，收纳：

- `比赛`
- `队伍`
- `模板`
- `云配置`

设计理由：

- 这些内容都属于后台运维的前置配置，而不是值班首页
- 它们之间联系紧密，拆成一级导航会造成主导航过碎
- 管理员的主工作流应该是“看总览 -> 看实例 -> 看任务 -> 必要时回到配置”

## 5. 关键页面职责

### 5.1 靶场总览页

`/admin`

核心目标：5 到 10 秒内让管理员建立系统当前态势认知。

页面结构建议：

- 顶部概览区：标题、环境说明、最后刷新时间
- KPI 区：运行中靶场、创建中任务、失败实例、已销毁实例或最近活跃模板
- 重点列表区：
  - 最近任务
  - 异常实例
  - 最近可访问入口

不建议：

- 首屏堆叠大量表单
- 首屏只展示比赛/队伍数量
- 首屏只做 marketing 风格 hero

### 5.2 靶场实例页

`/admin/range-instances`

这是后台的主工作页之一。

页面必须支持：

- 按比赛筛选
- 按队伍筛选
- 按模板筛选
- 按实例状态筛选

列表层必须尽量直接提供：

- 队伍名
- 比赛名
- 模板名
- 当前状态
- 公网入口 IP/URL
- 最近任务状态
- 过期时间
- 错误摘要

详情层必须能展示：

- 实例基础信息
- 公网入口详情
- 资源摘要
- 最近一次任务
- 最近若干步骤日志

交互建议：

- 桌面端采用“列表 + 详情”分栏，提升排障效率
- 移动端退化为列表进入详情

### 5.3 编排任务页

`/admin/provision-jobs`

这是后台的排障与审计页。

职责：

- 查看 `create / destroy / retry` 任务
- 查看每个任务的当前状态
- 查看步骤级日志
- 明确失败发生在何处

页面必须体现：

- 任务类型
- 关联实例
- 触发人
- 开始时间
- 当前状态
- 失败摘要

任务详情必须体现：

- 步骤时间线
- 当前步骤
- 标准输出摘要
- 标准错误摘要
- 已解析出的关键信息，例如入口 IP、实例规格或失败原因

### 5.4 基础配置页

`/admin/settings`

本页不是简单表单堆叠，而是平台基础对象的管理页。

#### 比赛

职责：

- 创建、编辑、删除比赛
- 管理比赛说明与状态

#### 队伍

职责：

- 创建、编辑、删除队伍
- 关联所属比赛
- 维护联系人信息

#### 模板

职责：

- 创建、编辑、删除靶场模板
- 展示模板版本、云厂商、IaC 类型、模块入口
- 后续承接企业网络蓝图结构展示

#### 云配置

职责：

- 展示或维护当前阿里云运行相关配置
- 展示默认区域、可用区策略、实例规格策略等
- 后续也可承接 OpenTofu Runner 的健康状态

## 6. 认证与导航体验

### 6.1 登录流

- 访问 `/` 时直接跳转到 `/login`
- 选手若要进入后台，应通过 `/login` 页上的“管理员入口”跳至 `/admin/login`
- 管理员登录成功后进入 `/admin`

### 6.2 会话体验

后台应保留已登录态，刷新页面后仍可继续使用。

最小要求：

- 本地存储登录凭据或 session 标识
- 页面首次加载时自动恢复后台态
- 凭据失效时自动回到管理员登录页，并给出中文提示

### 6.3 导航一致性

后台所有一级页面需共享：

- 同一套侧边导航
- 同一套顶部标题结构
- 同一套状态色与按钮体系

避免出现：

- 登录页和后台页像两个完全不同的产品
- 不同页面按钮文案、状态色、间距风格明显不一致

## 7. 状态、错误与空态设计

### 7.1 加载状态

需要明确的加载态，不允许空白闪烁。

建议：

- 首屏用骨架屏或占位卡片
- 表格区用行级 skeleton
- 详情区用占位块

### 7.2 空状态

后台大量页面在早期会处于空数据阶段，因此必须设计空状态。

至少需要：

- 无比赛时的空状态
- 无队伍时的空状态
- 无模板时的空状态
- 无实例时的空状态
- 无任务时的空状态

空状态必须包含：

- 当前为什么为空
- 下一步建议动作

例如：

- “当前还没有靶场实例，请先在基础配置中创建比赛、队伍和模板，再发起创建任务。”

### 7.3 错误状态

错误提示必须用中文解释业务动作失败，而不是只暴露技术词。

例如：

- “管理员登录失败，请检查账号或密码。”
- “靶场创建任务提交失败，请稍后重试。”
- “任务详情加载失败，请刷新页面后重试。”

同时保留技术详情承载位，用于：

- 日志折叠区
- 错误摘要区
- 任务详情页

## 8. 视觉与交互规范

### 8.1 视觉基调

- 主品牌色：蓝系
- 背景：浅色工作区
- 导航：深蓝或蓝黑色块
- 卡片：高可读低噪音

### 8.2 信息层级

优先级必须清晰区分：

- 第一层：实例状态、任务状态、入口信息、失败告警
- 第二层：比赛、队伍、模板等上下文对象
- 第三层：原始日志、资源 ID、技术细节

### 8.3 交互原则

- 每个页面只保留一个主操作焦点
- 危险动作必须显式确认
- 创建和销毁动作要有明显差异
- 成功、失败、进行中状态要有稳定视觉语义

### 8.4 响应式规则

桌面端优先，但必须保证移动端可进入和基本可读。

至少满足：

- 登录页在手机上可正常使用
- 后台侧边导航在窄屏下可折叠
- 列表详情布局在小屏下可纵向退化

## 9. 与现有实现的对齐要求

当前前端实现里，后台主要逻辑集中在单个 `AdminConsole` 组件中。

这意味着后续实施时需要遵守以下方向：

- 不继续把所有页面逻辑堆进一个组件
- 路由层、页面层、区块层、数据请求层逐步拆分
- 把登录页、后台首页、实例页、任务页、基础配置页拆成独立边界

这不是为了做无关重构，而是因为当前设计已经明确存在多页面、多状态、多角色入口，不再适合继续单文件承载。

## 10. 验收标准

当这一轮前端改造完成时，至少应满足：

- 根路径不再显示英文占位 hero，而是跳转到 `/login`
- 有独立的 `/login` 与 `/admin/login`
- 管理员登录页是正式产品风格页面
- 管理员登录后进入中文后台
- 后台存在清晰的一级导航
- `靶场总览 / 靶场实例 / 编排任务 / 基础配置` 四类页面边界清晰
- 比赛、队伍、模板不再作为首页主叙事，而是归入基础配置

## 11. 明确不在本轮设计内的内容

本轮不展开：

- 公共官网
- 选手完整产品
- 判题与积分榜
- 复杂图表大屏
- 拖拽式拓扑设计器
- 多租户身份体系
- 完整 RBAC

这些内容后续可以补，但不应阻塞当前后台主线落地。
