# 实例变更与模板回写语义拆分设计

日期：2026-07-09  
状态：Draft

## 背景

当前实例详情页里的拓扑编辑存在两种不同语义：

1. 对当前运行中实例做临时运维/配置变更
2. 将实例当前拓扑状态回写为模板的新草稿

这两种语义之前没有被明确拆开，导致用户容易把“应用变更”理解成只改实例，而系统实际又可能把部分修改同步到了模板层数据，进一步造成：

1. 模板视图和实例视图相互污染
2. 用户在“靶场编排”页看到的模板和实际创建实例时读到的模板不一致
3. 无法清楚区分“临时实例调试”与“沉淀为模板版本”

## 目标

明确拆分实例态与模板态：

1. `应用变更` 只作用于当前实例
2. 新增 `更新编排拓扑` 按钮，用于显式把当前实例配置覆盖回模板当前草稿
3. 模板生成实例时，只读取模板数据，不读取实例数据
4. 实例详情页的编辑默认属于实例草稿，不自动污染模板

## 非目标

本次不处理：

1. 模板草稿冲突检测与合并
2. 多实例同时回写模板的复杂并发控制
3. 实例详情页新增/删除节点、修改连线
4. 模板历史版本回滚能力

## 核心结论

### 1. 三个按钮的语义固定

实例详情页拓扑结构区域改为 3 个动作：

1. `保存草稿`
   - 仅保存到 `RangeInstance.draftTopologyGraph / draftScenarioTemplateSpec / draftCompiledProvisionSpec`
   - 不下发云上变更
   - 不修改模板

2. `应用变更`
   - 仅基于实例草稿执行实例级 update job
   - 更新当前实例的运行态快照
   - 不修改模板

3. `更新编排拓扑`
   - 将当前实例的最新拓扑配置覆盖回来源模板的 `currentDraftVersion`
   - 同步更新模板主表快照
   - 不触发实例 apply job

### 2. 实例与模板的数据边界

#### 实例态

实例详情页中所有编辑，默认先进入实例草稿：

1. `draftTopologyGraph`
2. `draftScenarioTemplateSpec`
3. `draftCompiledProvisionSpec`

实例态是运行中资产的工作副本，允许与模板暂时偏离。

#### 模板态

模板态只在两种情况下变化：

1. 用户在“靶场编排”页面编辑模板并保存
2. 用户在实例详情页点击 `更新编排拓扑`

除此之外，实例级 `保存实例草稿` / `应用变更` 都不得改模板。

### 3. 模板回写策略

本次采用用户确认的策略：

- `更新编排拓扑` 直接覆盖模板当前草稿

具体行为：

1. 找到实例的 `templateId`
2. 找到模板的 `currentDraftVersion`
3. 用当前实例的最新拓扑快照覆盖模板当前草稿版本的：
   - `topologyGraph`
   - `scenarioTemplateSpec`
   - `compiledProvisionSpec`
   - `compiledSpec`
4. 同步模板主表对应字段

不做冲突阻断，不比较模板在实例启动后是否又被其他人修改。

### 4. 回写源数据选择

`更新编排拓扑` 的回写源优先级：

1. 若存在实例草稿，则使用实例草稿
2. 否则使用实例当前运行态快照

这样用户可以：

1. 先在实例详情里调配置
2. 还没 apply 到云上时，直接把这份结构保存成新的模板草稿

## 前端改造

## 实例详情页

拓扑结构页按钮调整为：

1. `保存草稿`
2. `应用变更`
3. `更新编排拓扑`

其中：

1. `应用变更` 保持实例级语义
2. `更新编排拓扑` 点击前弹确认框
3. 确认文案明确写出：
   - “将当前实例拓扑与配置覆盖为模板当前草稿”
   - “该操作不会自动创建/修改实例，仅更新模板草稿”

## 模板编排页

无需新增按钮，但需要保证：

1. 模板页打开时优先读服务端模板
2. 本地草稿缓存仅在与当前服务端持久化图一致时才恢复
3. 避免旧浏览器缓存把模板页重新盖回历史值

## 后端改造

### 新增模板回写接口

新增实例详情侧接口，建议形态：

- `POST /admin/ranges/:id/sync-template`

请求体：

```json
{
  "triggeredBy": "admin"
}
```

语义：

1. 读取实例
2. 校验实例必须关联模板
3. 读取实例草稿或运行态快照
4. 覆盖模板当前草稿与主表字段
5. 返回更新后的模板摘要或成功结果

### 保持现有实例接口语义不变

保留现有：

1. `PATCH /admin/ranges/:id/draft`
2. `DELETE /admin/ranges/:id/draft`
3. `POST /admin/ranges/:id/apply`

但要明确约束：

- 这些接口不得触碰 `RangeTemplate`

## 数据流

### A. 实例临时变更

1. 用户编辑实例详情页拓扑
2. 前端写入实例草稿
3. 用户点击 `应用变更`
4. worker 对当前实例执行 update
5. 更新实例 runtime 快照
6. 模板不变

### B. 回写模板草稿

1. 用户编辑实例详情页拓扑
2. 前端写入实例草稿
3. 用户点击 `更新编排拓扑`
4. 后端将实例草稿覆盖到模板当前草稿
5. 模板页下次打开时读取到新草稿
6. 实例运行状态不变

## 验证要求

### 功能验证

1. 在实例详情页修改 ECS 规格并点击 `应用变更`
   - 实例规格变化
   - 模板不变

2. 在实例详情页修改 ECS 规格并点击 `更新编排拓扑`
   - 模板变化
   - 实例不自动触发 apply

3. 先 `保存实例草稿`，不 apply，直接 `更新编排拓扑`
   - 模板应写入草稿值

4. 从模板重新生成实例
   - 应读取模板最新草稿，而不是历史实例数据

### 回归验证

1. 旧本地缓存不会覆盖服务端模板
2. `应用变更` 不再隐式修改模板
3. `更新编排拓扑` 不再修改当前实例运行状态

## 风险

1. 当前采用“直接覆盖模板当前草稿”，如果多人并行修改模板，后提交者会覆盖先提交者
2. 实例草稿可能包含只在实例态有意义的字段，回写模板时需要确保使用可编排字段集合
3. 模板主表与 `currentDraftVersion` 必须同步写入，避免再次出现两套模板数据

## 推荐实现顺序

1. 后端新增 `sync-template` 接口并保证只改模板
2. 前端实例详情页增加 `更新编排拓扑` 按钮与确认弹窗
3. 将现有按钮文案调整为 `保存实例草稿`
4. 增加 API / service / 前端联调测试
5. 做容器态 smoke 验证
