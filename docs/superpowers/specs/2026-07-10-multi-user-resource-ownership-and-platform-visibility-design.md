# 多账号资源归属与平台可见性设计

日期：2026-07-10
最近更新：2026-07-10
状态：Active

## 当前状态快照

当前仓库仍处于“单管理员后台”阶段：

1. 登录通过 `.env` 中的 `ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ADMIN_TOKEN` 直接校验
2. 前端 session 只保存一个全局 token，不保存当前用户 profile
3. 后端 `AdminAuthGuard` 只校验固定 bearer token，不解析当前登录用户
4. `RangeTemplate`、`RangeInstance`、单实例批次等记录虽然已有 `createdBy` 字段，但还不是可用于权限判断的真实用户归属模型
5. 镜像中心当前已拆成“平台收录镜像 / 阿里云自定义镜像 / 阿里云公共镜像”三层语义，但还没有个人镜像管理和多账号可见性规则
6. 靶场编排当前默认是全平台共享视角，还没有“平台拓扑 / 我的拓扑”的资源边界
7. 后台当前还没有独立的用户管理页面和多用户维护接口

这次设计的目标不是引入复杂权限平台，而是在现有后台上补齐：

- 多账号登录
- 用户角色
- 资源拥有者
- 平台可见 / 个人可见
- 基于登录用户的列表过滤和操作校验

## 1. 背景

平台正在从“单管理员工作台”演进为“多账号共用平台”：

1. 不同用户都需要登录并使用平台
2. 普通用户可以创建实例、导出镜像、维护自己的镜像和拓扑
3. 普通用户可以查看所有平台资源，但不能执行平台级收录动作
4. 用户自己的镜像和拓扑可以发布到平台，也可以回退为私有
5. `admin` 既是普通资源用户，也是全局管理者

现有实现里，登录、鉴权、资源归属、前端视图都还没有这些边界，因此需要一次系统性但尽量保守的设计收口。

## 2. 本次目标

本次设计只解决“多账号 + 资源归属 + 平台可见性”主链路，不延伸到审批流、复杂协作和多级权限。

目标如下：

1. 支持多个平台账号登录
2. 角色先只保留 `admin` 和 `user`
3. 平台资源和个人资源不拆表，直接在原有资源表上补字段
4. 镜像支持“平台镜像 / 我的镜像 / 云上镜像来源”三类视角
5. 靶场编排支持“平台拓扑 / 我的拓扑”双视角
6. 实例创建不额外限权，但实例和导出镜像必须保留创建人归属
7. 普通用户可查看全部平台资源，但不能执行平台级“从阿里云来源收录到平台”动作
8. 用户可以把自己的镜像或拓扑直接发布到平台，无需审核
9. 用户可以把自己发布的平台资源回退为私有，`admin` 也可以执行同样操作
10. 后端不再信任前端传入的 `createdBy`、`triggeredBy` 等身份字段，统一从当前登录用户推导
11. 新增 `admin` 专属的用户管理能力，用于创建和维护平台账号

## 3. 非目标

本轮不处理以下内容：

1. 多级角色体系
2. 审核流
3. 资源协作编辑
4. 发布历史 / 审批历史
5. 复杂分享权限
6. 平台资源版本审批
7. 细粒度到字段级的 ACL

## 4. 核心产品规则

### 4.1 角色规则

系统只保留两种角色：

1. `admin`
2. `user`

权限语义：

- `admin` 可以查看所有资源、管理所有资源、执行平台级维护动作
- `user` 只能维护自己拥有的资源，但可以查看全部平台可见资源

### 4.2 资源可见性规则

首期所有需要被平台共享的资源统一采用两种可见范围：

1. `private`
2. `platform`

语义如下：

- `private`：只有 owner 和 `admin` 可见、可操作
- `platform`：所有登录用户可见；owner 和 `admin` 可操作；其他普通用户只读

### 4.3 发布与回退语义

发布和回退都作用于同一条资源记录，不复制数据：

- 发布：`private -> platform`
- 回退：`platform -> private`

回退后：

1. 资源从平台列表消失
2. 资源仍保留在作者的“我的资源”列表里
3. 已经创建出来的实例不受影响
4. 已经克隆出的个人拓扑不受影响
5. 只是从回退时刻开始，其他用户不能继续从平台池中新增使用它

允许执行回退的人：

- 资源作者本人
- `admin`

### 4.4 平台可见不等于平台共编

平台资源对所有登录用户可见，但默认不允许所有人共同修改。

规则如下：

- owner 可以编辑自己的平台资源
- `admin` 可以编辑所有平台资源
- 非 owner 的普通用户只能查看和使用平台资源，不能直接修改

如果普通用户想基于平台拓扑改造，应先克隆到自己名下，再编辑个人版本。

## 5. 数据模型设计

### 5.1 用户实体

新增独立用户实体，首期最小字段建议如下：

- `id`
- `username`
- `passwordHash`
- `role`：`admin | user`
- `status`：`active | disabled`
- `createdAt`
- `updatedAt`

说明：

1. 登录使用用户名和密码
2. 密码只保存 hash，不保存明文
3. `disabled` 用户不可登录

### 5.2 资源归属字段

平台资源和个人资源不拆两套表，直接在原有资源表上补充字段。

首期需要补齐这两类字段：

- `ownerUserId`
- `visibility`

`createdBy` 不再承担权限判断语义，保留为展示性创建人标签或历史快照字段。

### 5.3 适用资源

同一套 owner + visibility 模型至少覆盖：

1. 平台镜像资产 / 个人镜像
2. 靶场编排模板 / 个人拓扑
3. 实例记录
4. 导出镜像记录

其中：

- 镜像、拓扑直接使用 `visibility`
- 实例列表默认按 owner 收口，不需要额外做平台共享视角
- 导出镜像记录默认归属到导出用户名下，必要时可发布到平台镜像池

### 5.4 单表方案

本次明确采用单表扩展方案，不采用“双表平台资源 + 双表个人资源”。

原因：

1. 用户已经明确要求不拆两套表
2. 发布后仍然是同一条记录，不符合复制式双表模型
3. 现有仓库里很多链路已经基于当前资源主表实现，单表补字段的改动面最小
4. 查询和权限判断虽然会多一层过滤，但整体复杂度可控

## 6. 登录、会话与鉴权设计

### 6.1 登录响应

`POST /admin/session` 不再只返回裸 token，而是返回：

- `token`
- `profile`
  - `id`
  - `username`
  - `role`

### 6.2 前端 session

前端 session 存储从“只存 token”升级为“存 token + 当前用户 profile”。

首期前端至少需要获得：

1. 当前登录用户 id
2. 当前用户名
3. 当前角色

后台壳右上角可直接展示当前用户和角色，便于后续各页面消费相同上下文。

### 6.3 后端鉴权

当前固定 token 的 `AdminAuthGuard` 需要替换为真正的登录用户守卫。

新 guard 的职责：

1. 校验 bearer token 是否有效
2. 解析出当前用户
3. 把当前用户挂到 request 上

控制器和 service 不再信任 body 里传入的 `createdBy`、`triggeredBy` 等身份字段，而统一从当前登录用户上下文读取。

### 6.4 权限判断最小原则

后端权限收口时只保留三条核心判断：

1. 是否 `admin`
2. 是否资源 owner
3. 是否资源 `visibility === platform`

避免在首期引入更复杂的 ACL 结构。

## 7. 用户管理设计

### 7.1 页面入口

后台新增 `用户管理` 模块，仅 `admin` 可见并可访问。

普通用户：

- 不显示导航入口
- 直接访问对应路由时返回无权限

### 7.2 首期能力范围

首期用户管理只做最小必要动作：

1. 用户列表
2. 创建用户
3. 设置角色
4. 重置密码
5. 启用 / 禁用用户

本轮不做：

- 用户自注册
- 找回密码流程
- 角色组
- 批量导入

### 7.3 安全约束

为了避免把平台锁死，用户管理需要至少遵守以下约束：

1. 不能禁用最后一个活跃 `admin`
2. 不能把最后一个活跃 `admin` 降级为 `user`
3. 被禁用用户立刻失去登录能力

### 7.4 页面形态

用户管理页延续现有工作台列表页风格：

1. 顶部是用户列表标题和说明
2. 中间是搜索、筛选和创建按钮
3. 列表展示：
   - 用户名
   - 角色
   - 状态
   - 创建时间
   - 最近更新时间
4. 行级操作提供：
   - 重置密码
   - 角色切换
   - 启用 / 禁用

这样能与现有后台壳和列表页模式保持一致，不额外引入新型页面骨架。

## 8. 镜像中心设计

### 8.1 页面结构

镜像中心保留现有主壳，但顶部切成三个稳定视图：

1. `平台镜像`
2. `我的镜像`
3. `云上镜像来源`

这样可以最大化复用当前页面结构和测试资产。

### 8.2 平台镜像

平台镜像视图展示 `visibility = platform` 的镜像。

规则：

- 所有登录用户可见
- 所有登录用户可用于实例创建
- owner 和 `admin` 可维护
- 非 owner 普通用户默认只读

建议在列表中展示创建人 / 发布人，方便识别资源来源。

### 8.3 我的镜像

我的镜像视图展示 `ownerUserId = 当前用户` 的镜像。

规则：

1. 新导出镜像默认进入这里
2. 默认状态是 `private`
3. 用户可以编辑自己的镜像元信息
4. 用户可以把自己的镜像发布到平台
5. 已发布的镜像仍然继续留在“我的镜像”里，因为它仍然属于该 owner

也就是说：

- “我的镜像”是按归属筛选
- “平台镜像”是按可见范围筛选
- 同一条已发布记录可以同时出现在两边

### 8.4 云上镜像来源

云上镜像来源保留当前的阿里云公共镜像和自定义镜像来源语义。

规则：

- 所有登录用户都可以查看
- `admin` 可以执行“收录到平台”
- 普通用户不能执行平台收录动作

这部分满足“普通用户可查看所有镜像来源，但不能操作镜像中心的平台收录”。

## 9. 靶场编排设计

### 9.1 页面结构

靶场编排采用与镜像中心一致的双视图：

1. `平台拓扑`
2. `我的拓扑`

### 9.2 平台拓扑

平台拓扑展示 `visibility = platform` 的 `RangeTemplate`。

规则：

- 所有登录用户都可以查看
- 所有登录用户都可以基于它创建实例
- owner 和 `admin` 可以编辑 / 删除 / 回退
- 非 owner 普通用户默认只读

### 9.3 我的拓扑

我的拓扑展示 `ownerUserId = 当前用户` 的 `RangeTemplate`。

规则：

1. 用户创建的新拓扑默认归自己，默认 `private`
2. 用户可发布自己的拓扑到平台
3. 已发布拓扑仍保留在“我的拓扑”
4. 用户可把自己发布的平台拓扑回退为私有

### 9.4 克隆规则

普通用户如果想基于平台拓扑修改，不直接编辑别人的平台资源，而是使用现有 clone 能力：

1. 克隆一份到自己名下
2. 新记录默认 `private`
3. owner 变成当前登录用户

这样最符合现有仓库能力，也避免协作编辑。

## 10. 实例与导出镜像设计

### 10.1 实例创建

实例创建本身不额外限权，只校验当前用户对引用资源是否有可见性：

- 可见的平台拓扑 / 平台镜像可以用
- 自己的个人拓扑 / 个人镜像可以用
- 不可见的他人私有资源不能用

### 10.2 实例归属

实例创建时，后端直接从当前登录用户推导：

- `ownerUserId`
- `createdBy`

不再允许前端自己传 `triggeredBy`、`createdBy` 来决定归属。

### 10.3 实例列表

实例页按人收口，不再引入平台共享列表：

- `admin` 可查看全部实例
- 普通用户只能查看自己的实例

列表中继续明确展示创建人字段。

### 10.4 导出镜像

实例导出镜像时：

1. 后端自动把导出镜像归属到当前登录用户
2. 默认进入“我的镜像”
3. 默认 `visibility = private`
4. 用户后续可自行发布到平台

## 11. 接口收口

### 11.1 身份字段去前端化

本轮一个关键原则：

前端继续传业务字段，但不再传身份字段。

继续由前端传：

- `name`
- `templateId`
- `expiresAt`
- 业务表单字段

从 DTO 中删除或停止信任：

- `createdBy`
- `triggeredBy`
- 其他可被伪造的身份字段

### 11.2 用户管理接口语义

用户管理接口只给 `admin` 使用。

首期至少需要：

1. 用户列表
2. 创建用户
3. 更新用户角色
4. 更新用户状态
5. 重置用户密码

实现上不要求一次性做复杂管理台，但必须让 `admin` 能完成平台账号维护闭环。

### 11.3 镜像接口语义

镜像相关接口需要明确区分几类动作：

1. 平台镜像列表
2. 我的镜像列表
3. 发布到平台
4. 回退为私有
5. 平台收录
6. 云上来源查询

实现形式可以是：

- 新接口
- 或在现有接口上增加 scope / view 参数

本次设计不强制要求 REST 形态完全重写，优先最小改动。

### 11.4 拓扑接口语义

`RangeTemplate` 需要新增或扩展以下语义：

1. 平台拓扑列表
2. 我的拓扑列表
3. 发布
4. 回退
5. clone 到自己名下

创建默认写：

- `ownerUserId = 当前用户`
- `visibility = private`

### 11.5 平台级维护动作

只有 `admin` 可以执行的平台级动作包括：

1. 从阿里云来源收录镜像到平台
2. 其他已存在的平台目录维护动作中明确属于“平台运营”的动作

owner 虽然可以把自己的资源发布到平台，但不等于获得平台运营级来源收录权限。

## 12. 数据迁移策略

### 12.1 默认管理员

迁移时先创建默认管理员用户：

- `admin`

其用户名和密码初始值可继续从环境变量或初始化脚本生成。

### 12.2 旧数据回填

历史数据迁移规则尽量保守：

1. 如果历史记录的 `createdBy` 能匹配到已存在用户名，则补 `ownerUserId`
2. 不能匹配的记录默认归到 `admin`
3. 当前已经被平台共享使用的模板和平台镜像资产，默认回填为 `visibility = platform`
4. 迁移优先保证老系统已有资源继续可见，不把当前公共资源意外隐藏起来

### 12.3 默认可见性

对现有数据的默认可见性建议如下：

- 现有平台镜像资产：`platform`
- 现有模板：若当前业务默认全员可见，则回填为 `platform`
- 新创建的个人资源：默认 `private`

## 13. 测试与验证

### 13.1 行为测试重点

首期最重要的是权限和归属行为测试。

最小测试集至少覆盖：

1. `admin` 登录成功
2. 普通用户登录成功
3. 禁用用户登录失败
4. 普通用户不能访问用户管理接口和页面
5. 不能禁用或降级最后一个活跃 `admin`
6. 普通用户只能看到自己的实例
7. `admin` 能看到所有实例
8. 普通用户能看到所有平台镜像和平台拓扑
9. 普通用户不能执行平台收录
10. owner 可以发布自己的镜像 / 拓扑到平台
11. owner 可以把自己发布的平台资源回退为私有
12. 非 owner 普通用户不能编辑别人的平台资源
13. 实例创建和导出镜像时，后端自动写入当前登录用户，不信任前端传值

### 13.2 前端验证重点

前端只验证关键视图和权限状态，不拆两套页面：

1. 登录后顶部可看到当前用户身份
2. 镜像中心可稳定切换：
   - `平台镜像`
   - `我的镜像`
   - `云上镜像来源`
3. 靶场编排页可稳定切换：
   - `平台拓扑`
   - `我的拓扑`
4. 普通用户和 `admin` 看到同一页面时，只是按钮权限不同，不分裂成两套页面实现

### 13.3 容器态验证

按仓库约束，只要涉及前端、后端、worker 或 OpenTofu 行为改动，交付前都必须：

1. 更新相关容器镜像
2. `docker compose up -d --build`
3. 在容器态下验证登录、列表、发布/回退、实例创建等主链路

不以本地 dev server 替代容器验证。

### 13.4 阿里云 smoke test

阿里云 smoke test 仅做一次受控验证，覆盖最关键闭环：

1. 普通用户登录
2. 使用平台拓扑或个人拓扑创建实例
3. 检查实例记录创建人
4. 导出个人镜像
5. 将个人镜像发布到平台
6. 验证其他用户可见
7. 测试后立即销毁临时云资源

## 14. 实施顺序建议

推荐按以下顺序分阶段落地：

1. 用户模型、登录会话、request 当前用户上下文
2. 用户管理页面和用户维护接口
3. 资源表补 `ownerUserId`、`visibility` 并完成数据回填
4. 后端列表查询和写入权限收口
5. 前端登录态、导航、镜像中心、靶场编排页切成平台 / 我的双视图
6. 实例创建、实例列表、导出镜像改为后端自动写创建人
7. 容器构建与容器态回归
8. 最后做一次受控阿里云 smoke test

## 15. 结论

本次设计采用“单表资源 + owner + visibility”的最小可行方案：

1. 不拆平台表和个人表
2. 不引入审核流
3. 不引入复杂协作
4. 平台资源对所有用户可见
5. 资源仍由作者本人和 `admin` 维护
6. 所有创建人与触发人身份统一由后端从当前登录用户推导

这个方案最符合当前产品边界，也最贴合现有仓库结构，能在不打散已有主链路的前提下完成多账号资源治理的第一阶段。
