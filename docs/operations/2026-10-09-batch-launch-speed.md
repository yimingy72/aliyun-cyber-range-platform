# 批量单实例启动优化

## 运行方式与边界

新单实例仍由 OpenTofu 创建、持有 state 和销毁。一个批次对应一个工作区，每台 ECS 是独立资源，owner、云账号 UID/context、地域、网络、成员与作业归属保持固定。

运行时 OpenTofu 版本仍为 1.13.1。阿里云 provider 使用 `1.282.0-range.1`，基于官方 v1.282.0、commit `501318273fb83fabb981d45383d2fd7075ec7c8a`。唯一资源行为补丁是 ECS 创建首次状态查询等待从 10 秒改成 2 秒；Running 目标、NotFound 重试、超时、后续至少 3 秒的退避和删除等待保持原样。较早查询不会使云端自身的创建变快，也不保证每台固定省 8 秒。

源码补丁、固定来源摘要、Docker 构建和验证在 `scripts/provider/alicloud-fast-wait/`。定制 ZIP 的 SHA256 为 `9d9a30cacfd70d8307bfe0bc55b98cc95ca34c30f942264eac60a65ef5535f5b`。实际重复构建产物一致，1151 个资源的完整 provider schema 与官方相同。

## 并发配置

| 设置 | 默认值 | 含义 |
| --- | ---: | --- |
| `PROVISIONING_WORKER_RANGE_CONCURRENCY` | 2 | 每个 worker 同时执行的编排任务数 |
| `PROVISIONING_WORKER_SINGLE_BATCH_CONCURRENCY` | 3 | 每个 worker 同时执行的单实例批次数 |
| `OPENTOFU_PARALLELISM` | 10 | 每个编排图的资源并发 |
| `OPENTOFU_SINGLE_INSTANCE_PARALLELISM` | 20 | 每个独立实例批次的资源并发，允许 1–32 |

50 台同批通常形成约三轮流水处理。它们共享一次初始化与计划，不为每台启动独立 CLI。三个批次可产生约 60 个 ECS 并发资源操作；多个 worker 还会放大总量，同一账号的云 API 限流额度仍共享。

## 成员进度与恢复

Runner 仅解析 OpenTofu JSON UI 的已完成资源身份，不把原始诊断或敏感输出交给进度观察器。服务在 250ms 内合并事件，按精确云 ID 批量核验 Running、公网 IP 和完整归属标签；尚未就绪的成员每两秒重查。

成员可以先显示 Running/IP，整批作业仍运行。观察器不读取 apply 正在写入的 state，不提交账单或提前宣布作业成功。apply 结束后先停止并等待观察器，再读取完整 state 完成核验和提交。已核验的云 ID 保留供失败恢复使用。

创建期间的销毁、重启和打包会被拦截。重试请求冻结创建/销毁方向；旧重试任务缺少该信息时不提前显示 Running。失租或取消后停止观察，正常恢复仍受数据库批次租约和成员作业认领保护。

后台资源对账对 OpenTofu 单实例采用独立路径：云读取在锁外，随后在短控制锁内重读实例与当前作业。仅已成功完成且账号、上下文和完整标签一致的成员允许恢复摘要和账本；在途或失败待恢复任务不被抢写。该路径不再重打由 provider 管理的磁盘标签。

## 账单查询

生命周期账本同步、释放改为按 `rangeInstanceId` 索引查询，避免每台读取全站历史。唯一资源碰撞要核对账号、owner、实例、批次；并发插入后精确重读，保留首次计费时间。只有完全同归属的旧账本可回填已验证账号 UID。

Docker PostgreSQL 的 10,000 条背景账本、50 台各 ECS/磁盘场景中，历史查询返回量从 505,000 行降到 100 行；首次写入 100 条台账约 0.4–0.5 秒。该数据是数据库 fixture 测量，不是实云启动倍数。

## 验证与实云测量

容器回归覆盖 1569 项自动测试、两项真实 CLI mock-provider 规划测试、模块与示例 fmt/init/validate、生产构建；另验证了 provider waiter、schema 等价、旧 lock 正常升级及 state 保留。真实 CLI 的 50 个本地资源完成事件在整个 apply 返回前送达；这项测试不创建云 ECS。

当前平台两台 2c4g、40GiB、同镜像批次的入队到作业完成为 10.582 秒，上轮官方 provider 样本为 16.219 秒，旧 API 样本为 5.983 秒。本次两台销毁为 16.729 秒；不同样本的销毁前运行时长不同，不作为严格的销毁提速对照。

## 升级与回滚

先等待资源作业结束并备份工作区，运行 `pnpm provider:build`，将输出 mirror 以只读方式挂载，重建 API 与 worker 镜像。运行时必须通过固定 ZIP 摘要验证。已有已识别的 Alibaba Cloud 约束仅更新到精确的定制版本，再由正常 `init -upgrade` 更新 lock；不删除 state、不重标官方 ZIP、不使用生产 `dev_overrides`。

回滚同时使用保留的旧应用镜像与官方 provider mirror，并在无在途任务时操作。不能只把新模块的 mirror 换回官方 ZIP，因为新模块精确要求定制版本。
